## Findings by sub-question

### 1. How is it determined which capabilities a task needs

- **GPT-5's real-time router** (OpenAI, production, live in ChatGPT) — a learned classifier runs before generation and decides, per message, between a fast/general model and a deeper-reasoning model based on "conversation type, complexity, tool needs, and explicit intent." Source: OpenAI's own "Introducing GPT-5" post, via WebSearch aggregation (fetch blocked 403 — Medium, not Confirmed at primary-artifact level).
- **RouteLLM / vLLM Semantic Router** — a pre-classification step scores the *request itself* (not a decomposed task list) against a calibrated threshold or against embedding similarity to labeled task categories, and that score stands in for "what capability tier is needed." Source: RouteLLM GitHub + docs (Established/Medium, via search); Red Hat Developer's semantic-router writeup (fetched directly — BERT embeddings compared against task vectors).
- **Anthropic Skills' own progressive-disclosure trigger** — capability need is decided by matching the task's own wording against a Skill's `name`+`description` (always-loaded), not a separate classifier — already documented in this project's own `CAPABILITY_MAP.md` Capability 7/8, reconfirmed here as the same mechanism this project's own `skills/reverse-engineering/SKILL.md` and this session's other active skills rely on.
- **Trade-off**: all three mechanisms decide capability-need automatically, but at different resolutions — GPT-5's router decides per-message which *whole model* to use; RouteLLM/semantic-router decide per-request which *model tier*; Skill-matching decides per-task which *named capability* to load. None of the three decides *within* one task which of several already-available tools/models should each be used for which sub-part — that composition (a plan with several capability-needs inside one task) was not found solved by any single mechanism in this batch.

### 2. How the agent discovers available Skills/tools/plugins

- **Anthropic tool search tool** (`tool_search_tool_bm25_20251119` / `tool_search_tool_regex_20251119`, GA on the Claude API) — official docs, fetched directly in full. Mechanism: every tool's full definition is still sent server-side on every request, but tools marked `defer_loading: true` are excluded from the context/prompt prefix; when the model calls the search tool (BM25 natural-language or regex), the API returns up to 5 `tool_reference` blocks, which the API then auto-expands into full definitions inline. A typical 5-server MCP setup (GitHub/Slack/Sentry/Grafana/Splunk) costs ~55k tokens loaded up front; deferred + searched loading measured an >85% reduction, loading only the 3-5 tools actually needed. Explicit numeric limitation stated in the same docs: tool-selection accuracy measurably degrades past 30-50 available tools without this mechanism — this is Anthropic's own stated number, not an inferred one.
- **MCP Registry** (official, preview launched 2025-09-08, `blog.modelcontextprotocol.io`) — discovery is publish-side: a server publishes `server.json` at a `.well-known/mcp/server.json` path and the Registry indexes it; client-side "marketplaces" (mcp.so ~20k servers, smithery.ai, glama.ai) are sub-registries built on top. This is developer/operator-time discovery (deciding what to connect), not the running agent discovering new capabilities mid-task — a distinct mechanism from Anthropic's tool search, which operates *after* connection, at inference time.
- **Trade-off**: tool search solves "which of my already-connected tools is relevant now"; the MCP Registry solves "what could I connect at all" — no mechanism found in this batch that lets a running agent autonomously decide to connect a *new, not-yet-installed* MCP server mid-task; that step stayed a human/operator action in every source checked.

### 3. How a specific tool is selected among available ones

- BM25/regex tool search (above) ranks by textual/keyword match over name+description+argument fields, returns top-5, model picks from the returned set — a retrieval step, not a learned preference model.
- Red Hat's semantic router selects by embedding-similarity to labeled task-category vectors (a small BERT classifier), not by textual keyword match — a different selection mechanism solving the same class of problem for *model* choice rather than *tool* choice, evidence it generalizes across capability types.
- **Anti-pattern, Anthropic's own stated number**: without a discovery/ranking step, selection accuracy among tools measurably drops once the tool count passes roughly 30-50 — named directly in the same official docs above, not inferred from a vendor's marketing framing.

### 4. How a model is selected per subtask (not one model for everything)

- **Confirmed automatic, single-vendor**: GPT-5's router (above) — the only mechanism found in this batch where *choice of model* is itself a live, learned, per-message decision made by the system rather than configured in advance by a person. Trained continuously on real usage signals: user-initiated model switches, response preference rates, and measured correctness — i.e. the router's own policy is retrained from behavioral feedback, not fixed once. Confidence: Medium (WebSearch-aggregated paraphrase of OpenAI's own post; direct fetch blocked, not independently re-fetched from a mirror this session).
- **Confirmed, but manual not automatic, cross-vendor**: the "Claude implements, Codex reviews" pattern (multiple practitioner blogs — MindStudio's OmniAgent/Polly write-ups, a Hermes-agent-skill post, a DEV Community multi-agent pipeline post) is a *human-designed, static* pipeline: an engineer decides in advance which vendor's model plays which role, because the two vendors' models are observed to make different classes of mistakes ("a bug Claude overlooks is often obvious to Codex, and vice versa"). No source in this batch shows a runtime policy that itself decides, per subtask, "route this piece to Codex, that piece to Gemini, that piece to Claude" the way GPT-5's router decides among its own model family.
- **Not found**: an automatic, learned, cross-vendor (Claude/Gemini/Codex/other) per-subtask model router in production, as opposed to a same-vendor tiered-model router (GPT-5's fast/thinking split) or a hand-authored cross-vendor pipeline. This is an explicit gap, not a smoothed-over guess — it directly narrows what's actually provable about the "Models" layer the brief asked about: automatic selection is demonstrated within one vendor's own model family, not across vendors.
- LangGraph/CrewAI-style multi-agent frameworks *permit* assigning a different model to each node/agent, but every source found describes this as a design-time developer choice (whichever model is configured on that node), not a framework-level automatic decision policy comparable to GPT-5's router — corroborates the same gap from the framework side.

### 5. How systems optimize cost/tokens without losing quality — concrete mechanisms

- **Cascade with confidence threshold** (FrugalGPT, Stanford, cited via search — Established/Medium): send every query to the cheapest model first; check output against a confidence threshold; escalate to the next, more expensive model only if the threshold isn't met; stop at the first model whose answer clears the bar. Reported 50-98% cost reduction "with the same output quality" across benchmarks — i.e. the framing is explicitly *quality-preserving cost reduction*, not blanket cheapest-first.
- **Pre-classification threshold routing** (RouteLLM, ICLR 2025, Berkeley LMSYS + Anyscale — Established/Medium via search, GitHub not fetched directly this session): a router (matrix-factorization or BERT-based) scores query complexity once, compares it to a calibrated threshold α, and sends above-threshold queries to the strong model, below-threshold to the weak one. The threshold itself is calibrated by the operator against a target strong-model-call percentage (e.g. calibrate for 10% strong-model calls) — cost/quality trade-off is a dial the operator sets, not fixed by the framework. Reported: 85% cost reduction while retaining 95% of GPT-4-quality at MT-Bench, and 95% quality at only 14-26% strong-model calls when the router is additionally trained with LLM-judge-augmented preference data.
- **Provider-side prompt caching** — reusing the model's own KV-attention cache for a stable prompt prefix, at a stated 50-90% discount on cached input tokens (multiple caching-strategy write-ups, Established/Medium via search, consistent with Anthropic's own tool-search docs stating `defer_loading` is specifically designed not to break prompt-cache prefixes).
- **Semantic caching** (GPTCache and others) — a second, separate cache layer keyed by embedding similarity of the *query*, not the prompt text; a cache hit skips the model call entirely. Reported production hit rates cluster 20-45% (one cited real deployment: 76% total cost reduction, $10k/month to $2.36k/month, at a 95% hit rate) — but GPTCache's own claimed 67% hit rate depends on LLM-based equivalence detection layered on top of raw embedding similarity, i.e. the higher number requires an extra verification step, not raw vector search alone.
- **Programmatic tool calling** (Anthropic, official docs, fetched directly) — the model writes code that runs inside a sandboxed execution container and calls tools directly from that code, filtering/aggregating results before anything re-enters the model's context, instead of a full tool-result round-trip through the model for every call. Measured on BrowseComp/DeepSearchQA: +11% task performance and -24% input tokens versus tool calls without this mechanism; a separate PM-agent benchmark (75 tools) measured -38% billed input tokens with no accuracy change. This is the one mechanism in this batch with a *paired* accuracy-and-cost number, not cost alone — directly answers "without losing quality," not just "cheaper."
- **Tool search's `defer_loading`** (above) is itself a cost mechanism (85% context reduction) that is explicitly engineered to not touch the accuracy side negatively — Anthropic's own docs frame the *quality* benefit (selection accuracy above 30-50 tools) and the *cost* benefit (token reduction) as two separate, both-positive effects of the same mechanism, not a trade-off between them.
- **Real, named counter-risk (not smoothed over)**: several production-routing write-ups (LogRocket, NeuralTrust) independently name a "silent quality regression" failure mode — a request routed to a cheaper model produces a subtly worse answer (a missed nuance, a tool call that silently fails) with no dashboard signal, because nothing in a typical routing setup checks output quality per call; the same sources caution against building routing infrastructure at all below roughly $500/month in LLM spend, since the added complexity and latency (routing classifiers themselves add 50-100ms) isn't recovered at low volume.

### 6. How it's verified that a chosen capability was actually used and gave a result — not just called

- **Structured trace assertions** (Langfuse, LangSmith — both fetched via WebSearch, Medium confidence, official product docs not directly fetched this session): tool calls are recorded in the trace as structured fields (name, arguments, id, index) alongside which tools were *available* versus which were *chosen*; a code-level evaluator can assert a required tool was actually called with matching arguments, distinct from an LLM-judge step that separately rates whether the chosen tool actually fit the request and whether the final answer is grounded in the retrieved tool result (a "groundedness" rubric) rather than merely present in the trace.
- **Explicit, stated limitation**: the same sources state LLM-as-judge evaluators "need calibration against human labels to be trustworthy" — i.e. the verification layer itself is not self-certifying; a human-labeled reference set is required to trust the automated judge, which is a human-in-the-loop dependency inside a mechanism otherwise marketed as automated.
- **Real production instance, already in this project's own knowledge base** (`CAPABILITY_MAP.md`'s "External Validation" section, confirmed directly against Anthropic's own multi-agent research system post): an automated LLM-judge eval passed a version of the pipeline that was, in fact, choosing SEO content-farm sources over academic PDFs; only human evaluators caught this specific failure, and it was fixed with an informal prompt heuristic, not a structural check. This is a directly on-topic, real instance of "capability was called, a result was returned, and it still wasn't actually right" surviving automated verification.
- **Not found**: a fully automatic (no human-labeled calibration set, no dashboard review) mechanism, in any production system in this batch, that both catches a called-but-poor-quality tool/model result and does so with a claimed reliability number. Every verification mechanism found reduces the *volume* of cases needing human review; none eliminates the human step entirely.

### 7. How capabilities get updated when newer variants appear

- **Vendor-driven model lifecycle** (Anthropic's own `model-deprecations` docs, via search): four explicit states — Active / Legacy / Deprecated (with a named replacement) / Retired. This is the vendor publishing a migration signal; it does not, by itself, cause any consuming agent to switch.
- **Publish-side registry mechanism** (MCP Registry `server.json` at a well-known path, above): a *server* announces itself/its version; discovery happens when a registry or client re-crawls, not when a running agent notices a newer variant exists mid-task.
- **Single-practitioner automatic-pull mechanism** (joost.blog, fetched directly — single source, hobby-scale, not enterprise-validated): a `SessionStart` hook runs `npx skills update -g -y` on every session start, `/clear`, and context-compaction event, pulling the latest Skill content directly from a repo's `main` branch with **no release/version tag and no human approval step** — the author's own framing is "zero-friction," explicitly trading away a review gate for currency.
- **Explicit, real contradiction, not smoothed over**: the same search batch surfaced independent practitioner guidance (via Agensi's own skill-update write-up) that a **new model release should trigger a manual retest of every skill**, because a skill that worked cleanly on one Claude model can behave differently on the next — i.e. one real practice auto-pulls new skill *content* with zero human gate, while another explicitly requires a human to re-validate behavior after a model change, and neither source reconciles the two: auto-pulling a Skill update on `main` says nothing about whether that Skill still behaves correctly on whatever model version happens to be active when it's pulled.

### 8. Which of these mechanisms work fully automatically, without a human in the loop

- **Fully automatic in production, confirmed**: GPT-5's per-message router (Medium confidence — not independently re-fetched); RouteLLM/semantic-router's per-request threshold routing once deployed; Anthropic's tool search (BM25/regex + `defer_loading` expansion) — the model itself decides when to search and what to load, no human step per call; prompt caching and semantic caching (transparent to the calling agent); programmatic tool calling (the model itself decides to write code rather than call tools directly).
- **Not automatic — a human step is load-bearing even where the surrounding system is marketed as automated**: RouteLLM's cost/quality dial is a threshold an operator calibrates and chooses, not one the framework picks for itself; LLM-as-judge verification requires a human-labeled calibration set to be trusted; Anthropic's own advice to retest Skills after a model update is an explicit human gate; the joost.blog auto-pull mechanism removes the human gate for *pulling* an update but is single-source and explicitly silent on whether the pulled content is then re-validated at all; cross-vendor model-per-subtask pipelines (Claude implements/Codex reviews) are hand-designed once and then run automatically, but the *design decision* of which vendor does which subtask was never itself automated in any source found.

**Findings**:

- **Anthropic's own recommended role/cost split** (WebSearch-aggregated paraphrase of Anthropic's multi-agent research system post, Medium confidence — not re-fetched from the primary post this specific session, though this project's own `CAPABILITY_MAP.md` already has a Confirmed-tier direct fetch of the same post from an earlier session): lead agent on the more capable/expensive model (planning, judgment, synthesis, deciding when more research is needed), subagents on a faster/cheaper model for high-volume execution — an explicit statement that multi-agent systems burn roughly **15x** the tokens of a single chat turn, and are "best suited for tasks where the value of the outcome outweighs the expense" — i.e. the trade is named explicitly, not hidden.
- **Arize AI, "How cheap models changed multi-agent economics"** (fetched directly, full page) — names the same split as "orchestrator-executor": the orchestrator keeps "task decomposition, delegation, synthesis, verification, retries, and stopping decisions" (i.e. exactly the judgment functions), while executors get "bounded research, coding, extraction, review, and tool-heavy subtasks," optimized purely for cost per completed task. Cites a benchmark (BrowseComp) where a cheap-orchestrated worker team retained 96% of an all-expensive-model team's score at 46% of the cost. **Explicit, named risk, not smoothed over**: "cheap executors don't mean you can cheap out on the orchestrator" — decomposition/judgment quality has a real capability floor, and the same piece names a case (a cheaper frontier model swapped in) where the hallucination rate roughly doubled, tolerable for a supervised executor role but not for the orchestrator role. The article's own stated conclusion is to measure **cost per completed task** for the actual workload, not token price per model in isolation.
- **Claude Code's own official cost-management docs** (`code.claude.com/docs/en/costs`, fetched directly, full page, Confirmed) — concrete, primary-source mechanisms, not paraphrase:
  - Per-subagent model pinning is an explicit, documented, but **manual** configuration: `model: haiku` (or any model) can be set in a subagent's own definition; the general guidance is "Sonnet handles most coding tasks well and costs less than Opus. Reserve Opus for complex architectural decisions." This is a person's choice at authoring time, not a runtime policy.
  - **Agent teams are opt-in, off by default**: gated behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; official guidance states teams cost roughly **7x** a standard session (each teammate keeps its own full context window) and recommends "use Sonnet for teammates," "keep teams small," "shut down teammates when their work is done."
  - **Usage attribution, not automatic pruning**: `/usage` breaks down recent consumption by skill, subagent, plugin, and individual MCP server as a percentage of total — a visibility mechanism a human then acts on; it does not itself throttle or reassign anything.
  - **Explicit spend caps**: `--max-budget-usd`, workspace-level spend limits (Claude Console), and a documented per-team-size Tokens-Per-Minute/Requests-Per-Minute recommendation table (e.g. 200k-300k TPM/user for 1-5 users, down to 10k-15k TPM/user for 500+ users) — a rate-limit-shaped cap, set by an admin, not learned or adjusted automatically.
  - **Two mechanisms that *are* automatic, unprompted, no configuration required**: prompt caching (re-using the KV-cache for a stable prefix) and auto-compaction (summarizing conversation history near the context limit) are both stated as happening by default, not opt-in.
- **A named, sourced counter-finding on fan-out itself, not just its cost**: `systima.ai/blog/subagent-tax`, fetched directly, full page — an independent benchmark (three execution patterns: sequential, 2-subagent fan-out, 5-subagent fan-out, across several Claude model variants) found subagent fan-out used **2.6x-5.9x** the input tokens of doing the same work sequentially, **and was not faster on any measured task** (e.g. a 2-subagent lane took 8 minutes against a 4m15s sequential baseline). The authors state their own caveats plainly: cache-attribution measurement is unreliable through a gateway, one measured pairing mixed in unidentified model calls, and "this is one matched pair, not a distribution" — a real, self-flagged small-sample limitation, not a settled industry number. This directly qualifies every "fan out for speed" framing found elsewhere in this batch: parallelism here bought neither speed nor cost, only isolation (each subagent gets a clean, uncontaminated context) — a different, real benefit, but not the one usually advertised.
- **Corroborating real production issue, GitHub** (`anthropics/claude-code` issue #44968, "Excessive token consumption from uncontrolled parallel agent spawning," referenced via WebSearch aggregation — direct `gh`/API fetch attempted this session and failed, `gh` CLI not present in this environment; flagged Medium, not independently re-fetched) and issue #26179 ("Subagents should default to Sonnet, not inherit Opus") — a real, filed complaint that Claude Code's own default behavior is for a subagent to **inherit the parent's model** rather than default to a cheaper tier automatically, i.e. the cost-tiering-by-role pattern above is not the tool's own default; a person must configure it.
- **Practitioner consensus recommendation, independently repeated across several write-ups** (Builder.io, ClaudeKit, Agentropic, all WebSearch-aggregated, Medium): set a hard concurrency cap before fanning out at all ("ten subagents can trigger rate limits that stall your entire workflow... without a hard cap... you risk a denial-of-wallet attack on yourself"), fan out only genuine independent reads (keep writes single-threaded to avoid coordination cost), and price the fan-out against a measured single-agent baseline before adopting it — i.e. the same Capability-11 (Restraint) posture already logged in this project's own `CAPABILITY_MAP.md`, now reconfirmed specifically for the parallel-fan-out case, not a new principle.

**Net answer to the reinforced sub-question 5**: the real mechanisms for cost/token control under fan-out are (a) role-based model-tiering (expensive orchestrator, cheap executors) — found as both an official vendor recommendation and an independent benchmark with a paired quality number (96% score at 46% cost); (b) hard concurrency/spend caps, set by a human, not learned; (c) usage-attribution telemetry that informs a human decision, not an automatic one; (d) prompt caching and auto-compaction as the only two mechanisms confirmed to run with zero configuration. The named, load-bearing counter-finding is that fan-out's own most commonly advertised benefit — speed — did not hold up in an independent, self-critical benchmark; the mechanism's real payoff there was context isolation, not throughput, which is a different justification than the one usually given for building it.

## Addendum 2 — Mid-session clarification: periodic reassessment/pruning of capabilities, reinforcing sub-question 7

**Trigger**: coordinator relayed an owner-level distinction — "most current and well-packaged" is not the same target as "maximum coverage installed" — and asked specifically for a real (not hypothetical) mechanism that does *ongoing*, *periodic* reassessment/retirement/replacement of Skills/MCP/models already in place, not just a one-time setup choice, naming the risk explicitly: silent one-year accumulation of unused, unremoved capabilities.

**Findings**:

- **`mcp-audit`** (`rohitg00/pro-workflow`, `skills/mcp-audit/SKILL.md`, fetched directly, full file) — a real, shipped Claude Code Skill purpose-built for exactly this. Mechanism: **manually invoked** ("Use when: sessions feel slow or expensive, adding a new MCP server, context fills up quickly, reviewing project configuration" — symptom-triggered or ad hoc, not calendar-scheduled). It scores each connected MCP server on token overhead (a stated heuristic: 1-5 tools ≈200-500 tokens up to 30+ tools ≈3000+ tokens, "regardless of whether you use those tools"), cross-references actual usage this session and staleness ("haven't been used in 7+ days"), and flags functional overlap between servers. Output is a three-way classification — **KEEP** / **DISABLE** / **REVIEW** — with a projected token/dollar saving per recommendation. **Human approval is mandatory and explicit in the Skill's own rules**: "Never disable servers without user confirmation." Named target thresholds are stated as minimality goals, not maximality ones: fewer than 10 servers, fewer than 80 tools total, ideal.
- **`deadskills` and `skillreaper`** (via `bigprompthub.com`'s comparison, itself sourced from both tools' own READMEs, fetched directly) — two independently-built, real, shipped tools for the same problem at the Skill layer rather than the MCP layer. Both classify a Skill as **active / zombie / dead** using local transcript evidence (what the agent's own session history shows was actually invoked), not self-reported or assumed usage, and both are **manually invoked** (`npx deadskills`, a `reap` command) — neither tool's own documentation describes a cron/scheduled/automatic trigger. They diverge sharply on what happens next: **Deadskills is report-only** — its own README does not document automatic removal, and the comparison explicitly recommends treating its output "as reporting and analysis, then decide manually"; **Skillreaper takes a reversible action** — it can quarantine a flagged item into a `reaped/` directory with a manifest, and restore it later, i.e. cleanup that defaults to undoable rather than destructive. Both sources warn against treating a single low-usage reading as proof of dead weight, given "approximate token estimates" and incomplete transcript parsing as stated limitations.
- **Closest already-known internal analog, cross-referenced, not new this session**: this project's own `CAPABILITY_MAP.md` Capability 10 (Evaluation) already logs **eval-gated promotion** (`reaatech/prompt-version-control` — a version can't promote to production without passing an eval harness) as a real mechanism gating a capability's *arrival*; nothing in that entry, or newly found this session, describes an equivalent automatic gate on a capability's *departure* once installed and passing.
- **General-software analog checked and found not to transfer as claimed**: Dependabot/Renovate (GitHub/Mend's automated dependency-update bots) were checked directly as the closest well-known "periodic freshness check with an automatic PR" pattern from adjacent engineering practice. **No evidence found** that either tool, or an equivalent, has been applied to AI-agent capability inventories (Skills/MCP servers/model pins) specifically — search results describe them exclusively in their original scope (code package dependencies) plus one aside that AI coding agents increasingly *review* Dependabot-style PRs, which is a different claim (agents consuming this pattern for code) than the pattern being applied *to* agent capabilities themselves.
