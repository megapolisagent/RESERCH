# AI Intelligence (Researcher)

Прежде чем строить агента, продукт или принимать решение о профессиональной методологии — получите разведданные о том, как это реально устроено у сильнейших в мире, а не мнение и не поверхностный обзор.

## Что это

AI Intelligence реверс-инженерит реальную мировую практику по названной цели — агент, продукт, компания, профессиональный домен или идея будущего агента — и превращает в Intelligence Report с evidence. «Analyst, not researcher»: у каждой находки есть вывод «так что», не просто факт «нашла X».

## Что реально получаете — структура отчёта, не обещание

Один Intelligence Report на одну цель, всегда в этом порядке:

1. Лучшие реальные представители, найденные по цели, и почему
2. Механизмы, повторяющиеся почти у всех
3. Редкое, но выглядящее сильным
4. Что оказалось маркетингом
5. Что оказалось нерабочим
6. Что стало отраслевым стандартом
7. Подходы, которые противоречат друг другу — и какой trade-off принимает каждая сторона
8. Что переносится на исследуемую цель, а что явно нет — с причиной
9. Где источники расходятся — само расхождение, не сглаженное в один усреднённый вывод
10. Что изменилось недавно
11. Источники

**Никаких рекомендаций и «вам следует»** — только разведданные, вывод делает читатель сам.

## Как этим пользоваться — реальный пример

Инженер (Engineer) спросил: «Как реально устроена observability для самостоятельно живущих AI-агентов — не для дочерних суб-агентов внутри одной сессии». Разобраны 4 реальные системы на уровне механизма (Anthropic Managed Agents, OpenAI Responses/Conversations, OpenTelemetry+LangSmith, нативный механизм Claude Code), с честным «не найдено» там, где ответа не было, и явным разделением, что из найденного применимо к конкретному случаю, а что требует инфраструктуры, которой нет.

Один запрос — одна цель. Узкий вопрос (не полный отчёт) допускается, если критерий достаточного ответа зафиксирован до начала поиска — не подгоняется под то, что нашлось.

## Режимы

Два входа, не переключатель настроек:

| Вход | Когда | Что происходит |
|---|---|---|
| Названная цель/задача | Задача уже сформулирована словами | Работает напрямую, без знакомства |
| Первая встреча | `PROFILE.md` пуст, задача не названа | Короткое знакомство, не выдумывает факты о владельце |

Что не меняется никогда ни при одном входе: без evidence вывода нет, расхождение источников не сглаживается, рекомендаций не даёт.

## Механизмы доверия — конкретно

- **Иерархия источников, не единый вес всему найденному**: пять уровней достоверности от прямой первоисточника до маркетингового текста — подтверждено против практики human-intelligence tradecraft (ICD 203, Admiralty Code), не выдумано.
- **Verification — отдельная, гейтуемая стадия**, не часть общего сбора: строже отраслевого default для AI-agent систем, не пробел.
- **Review Loop — двойной контур**: обычная проверка находки плюс отдельный, более редкий пересмотр самого метода, инициируемый внешней стороной, не самим процессом.
- **Definition of Done** — что переносится на цель и что явно нет, с одной строкой причины на каждый источник, не просто список прочитанного.

## Когда обращаться, когда нет

| Обращаться | Не обращаться |
|---|---|
| Нужна реальная мировая практика по агенту/продукту/компании/профессии — с evidence, не мнением | Нужна рекомендация «что делать» — Researcher рекомендаций не даёт, только разведданные |
| Нужно проверить, действительно ли собственная методология подтверждена практикой, а не только собственными документами | Нужно техническое решение о том, как система Engineer устроена — это Engineering-граница, не Craft |
| Нужен узкий вопрос с зафиксированным до поиска критерием ответа | Тема без реального мирового прецедента — Researcher реверс-инженерит существующее, не изобретает с нуля |

## Чего Researcher никогда не делает

- Не даёт рекомендаций и не говорит «вам следует» — только интеллидженс, вывод — за читателем.
- Не сглаживает расхождение источников в один усреднённый консенсус.
- Не выдумывает факты о владельце и не выдумывает цифры/результаты — нет данных → `[УТОЧНИТЬ]` и вопрос, не догадка.
- Не решает вместо Engineer технические вопросы системы, в которой работает (граница Craft vs Engineering).
- Не молчит о пропущенном шаге Knowledge Growth — если реестры (`CAPABILITY_MAP.md`/`EVIDENCE_INDEX.md`/`MY_AGENTS.md`) не обновлены после исследования, это явно названная недоработка, не тихое умолчание.

## Практическая эксплуатация

Обновление служебной части — `bash update.sh`: обновляет только `skills/`/`instructions/`, личные файлы (`PROFILE.md`, `MEMORY.md`, `memory/`, `knowledge/`) не трогает никогда. Новые способности приходят только через `installer` из Skill System — не пишутся вручную в тело агента.

```text
├── UPDATE.md, update.sh                       ← безопасное обновление служебной части
├── DECISIONS.md, OPEN_QUESTIONS.md            ← история решений и открытые вопросы
├── ROUTING.md                                 ← что читать под конкретную задачу
├── instructions/
│   └── memory-rules.md                        ← полные правила трёх уровней памяти
├── skills/
│   └── reverse-engineering/                   ← собственная методология
│       ├── SKILL.md
│       └── references/
│           ├── PRINCIPLES.md                  ← зачем исследуем именно так
│           ├── METHODOLOGY.md                 ← пятистадийный процесс, иерархия источников, Definition of Done
│           └── REVIEW_LOOP.md                 ← как метод сам может меняться
├── knowledge/                                 ← накопленные разведданные, не метод
│   ├── CAPABILITY_MAP.md, EVIDENCE_INDEX.md   ← живой синтез
│   ├── MY_AGENTS.md                           ← портфель агентов владельца, сверка находок с ним
│   ├── cases/, evidence/                      ← сырой материал
│   └── MECHANISM_LIBRARY.md
├── memory/                                    ← дневник по дням
├── workspace/                                 ← результаты по ходу работы
├── research/AI-Engineering/                   ← историческое исследование, из которого выведена сама профессия Researcher
└── Foundation/                                ← историческая документация построения самого Foundation (01–03, 05–06);
                                                   04_REPOSITORY — отдельный самостоятельный git-репозиторий
                                                   (настоящая история Foundation), исключён из этого репозитория (.gitignore)
```
