# Capability Map — AI Agent Systems

Synthesis step between Stage 0A evidence collection and Stage 0B methodology synthesis. Not methodology, not a ruleset — this reorganizes everything logged in `knowledge/evidence/2026-08-03-stage0a-*.md` from "what did we find" (per-project) into "what fundamental capabilities do mature AI agent systems consist of, and what implementations of each capability recur across independent projects." Intended to be useful beyond this skill — to any future AI_OS agent reasoning about agent/system design (CDO, AI Architect, etc.), not only AI Intelligence.

Each capability lists: implementations found → which projects → which recurs most and why → trade-offs → recurring anti-patterns. Source letters refer to entries in the three evidence files (`...-ai-agent-systems.md` = A–L, `...-obscure-repos-experimental-systems.md` = M–Z, `...-workflows-issues-rfc-prompts.md` = AA–EE).

## Capability 1 — Memory

**Implementations found**:
- **Event sourcing** (append-only log, deterministic projection/regeneration, never edited in place) — Cortex, projectmem, ostk.ai, genesis-ssmp, agent6 (evidence E, M).
- **Vector/semantic** (embeddings + similarity search, e.g. HNSW) — Codemem, jcode, AWS sample agent's semantic namespace.
- **Graph-based** (typed nodes/edges: tags, clusters, semantic links, contradiction/supersession edges) — jcode, Codemem.
- **Episodic/handoff** (session summaries carried to the next session) — agent-memory/inosx, AWS sample agent's TaskEpisodes.
- **Multi-layer hybrid** (ephemeral session memory + durable cross-session memory as explicitly separate tiers) — AWS sample agent, agent-memory/inosx's five-layer stack.
- **Memory-as-Governance** (deterministic pre-action check against prior failures, not just passive recall) — projectmem (evidence F).
- **Cross-project/global promotion** (a lesson gated by signal strength — failures always promote, decisions only if explicitly tagged durable) — projectmem.
- **Tiered permanence, separate from projection** (every decision event kept permanently at storage layer — decay_rate = 1.0 — while its *default-view inclusion* is tiered active/aging/archived with automatic promotion back to active on access) — Jmeg8r/cortex. Resolves "never lose a decision" vs. "never overflow the token budget" by treating storage permanence and default-view inclusion as two independent knobs rather than one.

**Most frequent, and why**: event sourcing, independently found in 5 unrelated projects — the strongest single convergence in the entire capability map. It solves three problems at once (crash recovery, deterministic replay, audit trail) with one primitive (an append-only log), which is cheap to build and hard to get wrong compared to hand-maintained mutable state.

**Trade-offs**: event sourcing requires a projection/regeneration step and a compaction strategy for unbounded log growth; vector/graph memory adds embedding infrastructure cost in exchange for semantic (not just textual) retrieval; episodic/handoff memory is simplest to build but least structured, and is exactly where evidence U's real production failure (repeated, unrecognized-as-repeated reporting) occurred.

**Recurring anti-patterns**: a single mutable file the agent overwrites, with no audit trail (the thing event sourcing exists to replace); no dedup/contradiction handling, so a stale fact silently persists alongside a newer contradicting one (mitigated by pattern G — recency + explicit supersession, not deletion); no "have I already acted on/reported this" check before acting, causing token-burn loops (evidence U, the real "Sophie" case); untrusted external content entering memory unfiltered — memory poisoning, OWASP ASI06 (evidence H).

## Capability 2 — Planning

**Implementations found**:
- **Strategy/execution role separation** (a Director agent decides *what* to do, a separate agent executes it) — agentic-ceo (evidence S).
- **Declarative DAG planning** (Planner stage emits a dependency graph; scheduler resolves parallel execution levels) — both AgentFlow projects, SimpleAgents, hexdag, AgentsBear (evidence AA).
- **Reality-check gate before planning** (re-verify current state of every referenced item before committing to a plan; four-way status: NOT STARTED/PARTIALLY DONE/ALREADY COMPLETE/ASSUMPTION INCORRECT) — OpenCode Swarm (evidence P).
- **Single-owner planning discipline** (one Architect owns all decisions; one task executes at a time; every task QA'd before the next starts) — OpenCode Swarm.
- **Mission-to-DAG decomposition** (keyword extraction → search → directory bucketing → lease acquisition) — genesis-ssmp's "God" orchestrator.

**Most frequent, and why**: declarative DAG planning, found in five agent-orchestration projects — the same reasoning as evidence AA: hand-written dependency wiring is repetitive and error-prone, and dependency resolution is mechanical enough to automate.

**Trade-offs**: single-owner planning (OpenCode Swarm) trades parallelism for coherence, explicitly because "multi-agent systems fail when they're unstructured"; declarative DAGs trade expressive flexibility for predictability and auditability — every DAG-based project studied kept an escape hatch (shell steps, custom code) for what the declarative vocabulary can't express.

**Recurring anti-patterns**: planning against a stale assumption because nothing re-verified current state first (OpenCode Swarm's own stated motivation for building the reality-check gate); an architecture bet that optimizes the wrong dimension at planning time — e.g. premature microservices/multi-repo split chosen to save token cost, which cost more in coordination overhead than it saved (Sieve, evidence X) — a planning-level mistake, not an execution one.

## Capability 3 — Reasoning / Determinism Boundary

**Implementations found**:
- **LLM proposes structured intent, deterministic code owns control flow** — ai-runtime-lab, agent6, both unrelated AgentFlow projects (evidence N) — four independent instances of the single clearest rule in this whole map.
- **Workflow/Activity split** (orchestration must be 100% deterministic — no `time.now()`, no `random()`; only an Activity may touch the outside world, and each Activity is independently retried/cached) — ai-runtime-lab, modeled on the Temporal/Restate durable-execution pattern.
- **Finite-state-machine control** (states/events/transitions/guards; the LLM cannot pick the next state, only populate variables a downstream deterministic branch reads) — agent6's STATE_MACHINES.md.
- **Three-way failure taxonomy** (Retry: transient / Fail: permanent / Escalate: human-in-the-loop) — ai-runtime-lab, agent6 (evidence O).

**Most frequent, and why**: the determinism boundary itself (pattern N) — four independent small projects state the identical rule, sometimes in near-identical language ("the LLM never touches the outside world directly... it only proposes"). It recurs because free-text LLM output is unsafe to branch control flow on for the same structural reason unsanitized input is unsafe to use in a SQL query — the failure mode (silent, undebuggable non-deterministic replay divergence) is severe and easy to hit by accident.

**Trade-offs**: enforcing this boundary requires schema validation at every LLM output edge and real authoring discipline (ai-runtime-lab names it "non-negotiable" precisely because it's easy to violate without noticing); it constrains how much "judgment" can live inside the deterministic layer versus the LLM layer.

**Recurring anti-patterns**: putting `time.now()` or `random()` directly inside orchestration code that's supposed to be replayable (explicitly named, ai-runtime-lab); branching directly on free-form LLM text instead of a validated structured field; treating all failures identically instead of classifying into Retry/Fail/Escalate (undifferentiated retry wastes resources on permanent failures; undifferentiated abandonment gives up on transient ones).

## Capability 4 — Permissions

**Implementations found**:
- **Deny > Ask > Allow precedence, first match wins regardless of specificity** — Kimi-code, agentscope, agent-perms, intus-permission-rule-gate, and Claude Code's own documented permission system (evidence Z) — five independent implementations, the single strongest triangulation found in this entire research session.
- **Bare tool-name deny removes the tool from the model's context entirely** (vs. a scoped deny that leaves the tool visible but blocks matching calls) — the same five sources, converging on the identical distinction.
- **Chain-of-responsibility / ordered policy list architecture** — Kimi-code's explicit microkernel design (policies self-register, first hit wins).
- **Per-mode fixed evaluation order** (DEFAULT/EXPLORE/ACCEPT_EDITS/BYPASS/DONT_ASK, each with its own dispatch method) — agentscope; DONT_ASK mode carries an explicit invariant ("must never return ASK — every ask path is converted to deny") designed around the specific constraint of no human being available.
- **"Harness constraint" vs. true permission** — Kimi-code's distinct conceptual contribution: a mechanism that limits the agent for its own correctness (e.g. a plan-mode write guard) is a hard deny with no user-override channel, categorically different from a risk-policy ask/deny, which is always user-overridable.
- **Semantic command classification layered on top of pattern matching** (read/read-sensitive/write/admin × local/remote) — agent-perms, built specifically because glob-based rules are "fragile" (an admission from Claude Code's own docs, cited by agent-perms).
- **Compound-command anti-injection** — an allow rule for one command does not extend to that command chained with another via `&&` — intus.
- **Empirical permission-bounding via observed-run learning** — os-tack/ostk.ai's `ostk learn` runs a worker in observation-only mode, then emits the minimal permission grant from what was actually exercised, rather than a hand-authored or guessed allowlist. A named alternative to manually-authored permission rules; single-source, not yet cross-validated against a second project.
- **Intersection (most-restrictive-wins) composition**, as a distinct alternative to ordered deny>ask>allow — os-tack/ostk.ai composes multiple permission sources by intersection (a tier sets a floor no explicit pin can lower) rather than by first-match-wins ordering. Both are legitimate, independently-arrived-at answers to "how do multiple permission sources combine" — logged as two known approaches, not one universal rule.
- **External Dependency Checkpoint** — a mandatory human pause triggered specifically when a work unit needs external service credentials, before implementation of that unit begins — dsifry/metaswarm. Prevents an agent from silently stalling, fabricating a stub, or proceeding with broken integration when it lacks something only a human can provide; costs friction even when the human already has the credential ready.

**Most frequent, and why**: deny-first ordering with bare-name-removal, found identically in five otherwise-unrelated systems including a major vendor's own product. It recurs because it's the only ordering that can't be bypassed by an earlier, broader allow rule, and "remove the tool from context" vs. "block the call" is a distinction every serious implementation needs once agents have many tools of varying risk.

**Trade-offs**: category-based ordering (not specificity) means a broad deny always wins even over a narrow, deliberate allow — every source treats this as a deliberate safety trade, not an oversight; semantic classification adds real engineering cost that a simple glob rule doesn't.

**Recurring anti-patterns**: relying on glob/pattern matching alone to express command intent (can't distinguish `git reset --soft` from `git reset --hard`); treating a semantic classification/guardrail layer as if it were a full security boundary (agent-perms' own explicit disclaimer: "not a sandbox"); letting a hook's decision override the permission gate (Claude Code's own docs: hook decisions never bypass deny/ask rules).

## Capability 5 — Review

**Implementations found**:
- **Self-critique/Reflection family**: Generator-Critic split, single-agent self-reflection, multi-perspective parallel critics with an explicit arbitration role ("Resolver"), confidence-gated critic — three independent pattern catalogs (evidence I).
- **Frozen/fixed critique rubric**, applied identically every pass, to keep results comparable across iterations — multiple sources (evidence L), independently corroborating a design choice already made in this skill's own Evidence Review. dsifry/metaswarm sharpens this to a **binary-only verdict** (no "approved with comments") specifically to stop a reviewer softening a contract violation into a suggestion.
- **Mandatory fresh-reviewer instance with explicit self-escalation** — a reviewer that recognizes it has memory of a prior review is required to escalate rather than continue, because carried-over memory causes the reviewer to search for confirmation a fix worked instead of genuinely re-checking — dsifry/metaswarm. A distinct lever from "more parallel reviewers" (below): metaswarm gets anchoring-resistance from *guaranteed freshness* with a single reviewer, not from reviewer count — the two are independent, not substitutes for each other.
- **Asymmetric persistence by role** — the same system gives its producer agent persistent, no-cold-start memory across work units, while forcing every reviewer instance to be freshly spawned with no memory, "in both modes, without exception" — dsifry/metaswarm. The underlying reasoning: persistence helps a producer (continuity is valuable for building) and actively hurts a verifier (persistence is exactly what causes anchoring) — the same capability (memory) is correct for one role and wrong for another, rather than one policy applied uniformly.
- **Combined stopping conditions**: iteration cap + cumulative token budget + stagnation detection (identical critique output twice in a row ⇒ structural blind spot, not a hard problem) — three independent sources (evidence J).
- **Standing adversarial stress-test of the method itself**, not just of individual outputs — Anthropic's "Alignment Stress Testing" team (backlog item 4, world-practices batch); agentic-ceo's Critic agent, real-world-validated ("almost cut to save cost... without it the knowledge base becomes an echo chamber," evidence W).
- **Automated, continuous review loop** (Observer grades every run; Evolver adjusts config automatically based on Observer + Critic output) — agentic-ceo (evidence W) — review as a standing system, not only a periodic manual checkpoint.
- **RFC as a distinct pre-decision review stage**, with its own status lifecycle (Draft → In Review → Changes Requested → Approved/Closed → Blocked/Discarded), separate from the ADR decision record itself — evidence DD.

**Most frequent, and why**: the frozen-rubric + capped-iteration combination recurs across every self-critique implementation studied, because free-form review measurably drifts (the model invents new criteria each pass) and unbounded iteration is the most commonly named failure mode of the entire pattern family.

**Trade-offs**: same-model self-critique is explicitly flagged, across independent sources, as missing "correlated blind spots" (the critic shares the generator's own blind spots); multi-perspective parallel review costs 3-4× a single pass; a standing adversarial-review function (Anthropic's, agentic-ceo's) costs a dedicated role/budget that a smaller system may not be able to justify.

**Recurring anti-patterns**: "pocket veto" — review stalls with no explicit decision, until the author gives up (evidence DD); "approval by silence" — no comments, auto-accepted, no one actually agreed; "retrofit RFC" — code already written, the review is theater (evidence DD's own prescription: call it an ADR instead, don't pretend it's still a decision process); running critique without a frozen rubric, producing incomparable results across runs; no stopping condition, allowing a self-correction loop to burn up to 10× normal cost; a project's own label of "external" or "independent" review taken at face value — Jmeg8r/cortex's "external evaluation" document has no disclosed reviewer identity distinguishing it from a same-author, same-tool adversarial re-prompt, even though its content was genuinely useful. The label is a claim, not a verified fact; check for actual reviewer-identity separation before counting it as strong corroborating evidence.

## Capability 6 — Learning

**Implementations found**:
- **Blameless post-mortem culture applied to the *method* itself**, not only to incidents — Google SRE, Cloudflare, Anthropic RSP's own "Reflections" document — now triangulated three times independently (world-practices batch); this skill's own `REVIEW_LOOP.md` already follows the same shape.
- **Structured knowledge curation from review comments**: generalize a specific comment into a general fact, tag it with a confidence tier and full provenance (source, reference, date, author, context), and deduplicate by similarity — merging provenance and auto-upgrading confidence once ≥3 independent sources agree — dsifry/metaswarm's Knowledge Curator (evidence CC) — the most concrete, production-shaped implementation of source-triangulation-as-a-numeric-rule found in this entire map.
- **Automated mining of agent-generated output into an actionable, rate-limited, deduplicated backlog** — github/gh-aw's discussion-task-miner (evidence CC).
- **Self-tuning via a closed Observer+Evolver loop** — agentic-ceo (evidence W), overlapping with Capability 5.
- **A written culture document (not a rules file) that measurably shaped agent judgment** on situations no rule enumerated in advance — Katherine Cass's `AGENT_CULTURE.md` (evidence U).

**Most frequent, and why**: the "post-mortem culture applied to the method, not just the incident" pattern is the most consistently repeated, appearing in software engineering, infrastructure engineering, AI safety policy, and (via this skill's own design) technical-intelligence methodology — four different domains independently treat *how the practice itself improves* as a first-class, versioned, documented process rather than an informal habit.

**Trade-offs**: metaswarm's confidence-upgrade-at-3-sources threshold is a fixed, not empirically-derived, cutoff; automated self-tuning (Observer+Evolver) without a human checkpoint risks optimizing a proxy metric while drifting from the actual goal — a risk flagged by this map's own reasoning, not one any source reported having actually caught.

**Recurring anti-patterns**: treating a written specification/plan as equivalent to verified progress (deepelement-mind/openos's explicit three-lens fix: Target/IterationScope/Implemented, the last requiring evidence links, not just documentation — evidence Q); failing to check whether a lesson has already been logged before re-deriving or re-reporting it (evidence U, the token-burn case).

## Capability 7 — Context

**Implementations found**:
- **Three-level progressive disclosure**: name+description always loaded → full body loaded only on task match → linked files loaded only as needed — Anthropic Agent Skills (evidence B).
- **Static always-on context vs. dynamic on-demand context**, triangulated independently three times — Claude Code (AGENTS.md/CLAUDE.md), Cursor (`.cursor/rules/` vs. `.cursor/skills/`), OpenHands (repo skill vs. knowledge skill) (evidence C).
- **File-as-context abstraction**: large tool outputs are written to temp files instead of injected eagerly; the agent is given the path and decides whether to read/tail/grep it (Cursor's own architecture, per the reverse-engineering writeup used in tool-selection evidence).
- **Silent dynamic context injection** (open files, git status, linter errors, rules, skill summaries, terminal state, attached fresh on every message) — Cursor.
- **Context compaction/condensing** to manage token budget across a long session — Cortex, jcode, Cursor's own summarization pipeline.

**Most frequent, and why**: the static/dynamic split (Capability 7 and Capability 8 overlap here) is the most consistently, independently re-derived shape, because the underlying constraint — a finite context window holding content of wildly different relevance-persistence — is identical across every agent tool regardless of vendor.

**Trade-offs**: progressive disclosure and the static/dynamic split both depend entirely on correctly classifying content as "always relevant" vs. "conditionally relevant" at authoring time — misclassifying a conditional piece as always-on silently taxes every future task's budget.

**Recurring anti-patterns**: dumping an entire repository into context at once (explicitly called a bad idea in Cursor's own reverse-engineered architecture); eager injection of irrelevant context, which the same source states is "often worse than missing context because it actively misleads the model."

## Capability 8 — Skills

**Implementations found**:
- **SKILL.md packaged-directory format** (frontmatter `name`/`description`, markdown body, optional bundled reference files/scripts) — the Anthropic-originated standard, now also documented at agentskills.io (evidence B).
- **AGENTS.md as the complementary, cross-tool, repo-wide static file** — distinct from a Skill, adopted by 30+ tools under Linux-Foundation-stewarded governance (evidence A).
- **Repo skill vs. knowledge skill** — OpenHands' own terminology for the same static/dynamic split (evidence C).
- **"Fat engine, thin skill"** — keep the orchestrator/engine domain-agnostic; push all domain-specific behavior into one config file a Skill (or template) wraps — hermes-multi-agent-workflow's explicit design principle (evidence BB).

**Most frequent, and why**: same underlying convergence as Capability 7 — the packaged, metadata-first, load-on-demand shape recurs because it's the only way to scale the number of latent capabilities without scaling standing token cost.

**Trade-offs**: as Capability 7 — a Skill's discoverability lives or dies on the precision of its `description` field.

**Recurring anti-patterns**: maintaining a separate, duplicated instruction file per vendor tool instead of one shared cross-tool file — literally the problem AGENTS.md was created to solve; domain-specific logic leaking into the "engine" layer of a reusable template, defeating its reusability (hermes-multi-agent-workflow's own stated discipline against this).

## Capability 9 — Execution

**Implementations found**:
- **Sandboxed/jailed command execution** (Landlock+seccomp, namespaces, `pivot_root`, per-child-process jailing) — agent6.
- **Pluggable, swappable execution backends** (local / Docker / remote, same agent code across all) — OpenHands SDK's Workspace abstraction.
- **Speculative, draft-as-original-file edit application** for low-latency multi-file edits — Cursor's Composer architecture.
- **Per-mission resource budgets** (token/call caps) to prevent context or action thrashing — genesis-ssmp's Page-Fault Governor.
- **Controlled, metric-gated rollout with automatic revert** — Cloudflare's Health Mediated Deployments, applying the same discipline to configuration changes as to software releases after a real incident exposed the gap.

**Most frequent pattern class, and why**: budgeted, bounded execution (sandboxing, resource caps, gated rollout) recurs because unconstrained execution is the single highest-severity risk class in any of these systems — a bad tool call, a runaway loop, or a bad config change all cause real, external damage, unlike a bad memory entry or a miscategorized skill.

**Trade-offs**: sandboxing and containerized reproducibility cost real infrastructure and latency (SWE-bench's own harness needs 100–2000GB of disk and 16GB+ RAM depending on cache level); gated rollout requires well-defined, monitored success metrics per service, which is itself work.

**Recurring anti-patterns**: unrestricted terminal/network access without sandboxing (an explicit, named risk in Cursor's own architecture writeup); never having tested a specific failure mode (a full facility going offline) before it happened for real, only ever testing partial failures (Cloudflare's own documented incident cause).

## Capability 10 — Evaluation

**Implementations found**:
- **Containerized, reproducible evaluation harness** (layered base/environment/instance images, fixed prediction format, tunable cache levels, a numeric resolution-rate metric) — SWE-bench, with its own documented lesson (conda envs were "underspecified," replaced by Docker).
- **Structured, quantitative, comparative capability+risk reporting**, explicitly benchmarked against the previous model version, with reported confidence intervals — OpenAI System Cards (world-practices batch).
- **Standardized documentation template** (Model Details/Intended Use/Factors/Metrics/Evaluation Data/Training Data/Quantitative Analyses/Ethical Considerations/Caveats and Recommendations) — Mitchell et al.'s Model Cards.
- **Measurement validity theory** — checking whether a metric actually measures the claimed construct (systematize → operationalize → apply), distinct from checking where evidence came from — Microsoft Research (world-practices batch).
- **Eval-gated promotion** — a version cannot be promoted from staging to production unless it passes an evaluation harness first — reaatech/prompt-version-control (evidence EE), tying Evaluation directly to versioning/Review.
- **Confidence calibration against real outcomes** — a rolling log of (self-reported confidence, actual outcome) pairs with a learned correction factor, because raw self-reported confidence is measurably uncalibrated — Antigravity Lab's self-critique article (evidence K).
- **Adoption/UX friction scored with the same rigor as technical risk** — Jmeg8r/cortex's own risk analysis scores "setup complexity deters adoption" with the same Likelihood×Impact rubric as a technical failure mode, tied for the single highest score across 19 modes analyzed. Applies directly to this skill's own practice: adoption/usability risk of an investigated object should get an explicit score, not a softer unscored afterthought.

**Most frequent theme, and why**: every implementation here converges on the same underlying worry — a number or a "looks done" signal is not the same as verified correctness — appearing as benchmark saturation (a maxed-out benchmark stops discriminating between models, MSR), naive self-confidence (uncalibrated by default), and reproducibility drift (SWE-bench's own conda-era problem). Evaluation recurs everywhere specifically because every other capability's claims need to be checked against something external to be trustworthy.

**Trade-offs**: reproducible containerized evaluation is expensive; eval-gating adds shipping friction to gain regression safety; measurement-validity checks require real methodological sophistication most small teams don't invest in.

**Recurring anti-patterns**: treating a benchmark score as self-evidently meaningful without checking it isn't saturated or invalid for the claim being made; treating raw self-reported model confidence as calibrated without checking it against real outcomes; declaring "done" from a passing test suite alone without checking spec compliance or runtime state separately (evidence Y's explicit "three different claims" formulation).

## Capability 11 — Restraint / Scope Discipline

**Source**: AI Engineering profession investigation, 2026-08-11 (`research/AI-Engineering/03-full-report.md`), specifically its Stage 1.5 abstraction-tagging pass, which separated ten independently-converging findings into their own category once it became clear none of them were about a technology at all.

**Implementations found**:
- **Reach for the simplest primitive that solves the task, agent last** — Anthropic's own "Building Effective Agents" framing (augmented-LLM → workflow → agent, in that order of preference).
- **Own your control flow** — `humanlayer/12-factor-agents`, corroborated by ~100 founder interviews: the highest-revenue production agent systems keep the LLM's surface area narrow, with deterministic code retaining control flow.
- **Constrain agent fan-out to actual task complexity** — Anthropic's multi-agent research system named its own real failure mode (up to 50 subagents spawned for simple queries before this was deliberately capped).
- **Start with the fewest memory blocks that work** — Letta's own documented antipatterns name both "too few" and "too many" (10+ blocks when 3-4 suffice) as failure modes, i.e. minimalism is a design target, not just an absence of effort.
- **Recognize a missing reusable capability from an observed behavioral signal, not a hunch** — Anthropic's Skills team names the concrete trigger: an agent regenerating the same procedural work from scratch, repeatedly.
- **Surface genuine uncertainty inline instead of silently guessing** — `github/spec-kit`'s `[NEEDS CLARIFICATION]` convention.
- **Let a working prototype be the spec** — the Claude Code product team explicitly does not treat docs as source of truth; a ~10-minute build-to-feedback loop stands in for a written spec.

**Most frequent, and why**: this is the single most consistent finding across the entire investigation — every strong source treats agentic complexity, Skills, memory, MCP, and orchestration as a cost requiring justification, never a default. It recurs because it is judgment, not technology, and therefore doesn't get invalidated by the next model release or protocol version the way an implementation-level mechanism can.

**Trade-offs**: restraint is easy to state and hard to operationalize — every implementation above pairs the principle with a concrete, checkable trigger (a fan-out cap, a memory-block count, an observed regeneration behavior) specifically because an unenforced restraint principle degrades into "build it if it seems useful," which is the failure mode it exists to prevent.

**Recurring anti-patterns**: reaching for an agent/framework/Skill/memory system by default before confirming the task actually needs it (named explicitly as a mistake by multiple independent sources); unconstrained agent fan-out; treating a missing-Skill judgment as a vague feeling rather than checking for the specific regeneration signal.

**Relationship to other capabilities**: distinct from Capability 4 (Permissions, which governs what an agent is *allowed* to do) and Capability 9 (Execution, which governs how bounded work is *carried out*) — this capability governs whether a given piece of agentic machinery should be built or invoked *at all*, a decision that precedes both.

## Refinement — Orchestrator↔Specialist Invocation Contract (call/return/sufficiency/resume)

**Source**: 2026-08-12, direct question from Engineer (sibling Foundation repo, ENGINEER) about how the pattern orchestrator/main-agent → specialist/research-agent → verify result → refine → re-invoke is actually implemented in real, checkable systems — prompted by the two repos' own newly-proven direct-invocation channel (Engineer calling this Researcher directly, without the owner in the loop). Internal-context-first rule applied: `HOME.md`/`MISSION.md`/skill files/`MY_AGENTS.md`/`CAPABILITY_MAP.md` read in full before external search opened.

**Implementations found**:
- **Call-and-return, single session** — Claude Code subagents (`code.claude.com/docs/en/sub-agents`, official docs, fetched directly, version-numbered v2.1.x). Contract in: a prompt string is the *only* channel from parent to subagent — "the only channel from parent to subagent is the prompt string that the main agent writes when it delegates"; the subagent starts with fresh context (no parent history). Contract out: "the parent receives the subagent's final message verbatim." Sufficiency check: left to the calling Claude's own judgment — no built-in rubric. Refinement without restart: **resume** — "each subagent invocation creates a new instance with fresh context... to continue an existing subagent's work instead of starting over, ask Claude to resume it. Resumed subagents retain their full conversation history... The subagent picks up exactly where it stopped." Mechanically, resume is the `SendMessage` tool addressed to the subagent's returned agent ID or name; `SendMessage` also auto-resumes a stopped/completed subagent without a new `Agent` call.
- **Deterministic sufficiency gate, opt-in** — same docs, `agent-teams` page: `TeammateIdle` and `TaskCompleted` hooks can `exit 2` specifically "to send feedback and keep the teammate working" / "to prevent completion and send feedback" — a code-level, non-LLM check that can force refinement instead of accepting a self-reported "done." This exists alongside the default (LLM discretion), not in place of it.
- **Separate-session call/response, plain text only** — Claude Code **cross-session messaging** (`code.claude.com/docs/en/cross-session-messaging`, fetched directly). Two independent sessions (not one parent/subagent pair) reach each other by name via `SendMessage`/`ListAgents`; "a message is a piece of text one Claude writes to another, never conversation history or files" — the receiving session gets only that text, with a reply address, and can reply the same way. This is the mechanism for two *separately-run* Claude Code sessions/repos, structurally distinct from the subagent-resume case above even though both use the same `SendMessage` tool.
- **Orchestrator-worker with explicit task contract, no resume** — Anthropic's own multi-agent research system (`anthropic.com/engineering/multi-agent-research-system`, official post, fetched directly). Contract in: "each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" — vague short instructions were a named, real early failure mode. Contract out: subagents write to a filesystem / return a compiled result to the lead. Sufficiency check: the lead "synthesizes these results and decides whether more research is needed" — **explicitly implicit** in Anthropic's own writeup, no named rubric. Refinement: **if insufficient, the lead spawns additional subagents or refines its own strategy — it does not resume/reopen the subagent that already ran.** Named failure modes: duplicated work between subagents investigating overlapping scope, and unconstrained fan-out (50 subagents for simple queries).
- **Call-and-return via a structured primitive** — LangGraph supervisor (`langgraph-supervisor-py`, GitHub, function-level detail obtained via direct source search, not a raw dump — Established/Medium, not Confirmed). `create_handoff_tool` builds a tool that hands control (and a payload) to a named worker; `create_handoff_back_messages` constructs the message pair that returns control to the supervisor — call-and-return is explicit in the API, not incidental. `interrupt()` / `Command(resume=...)` pauses a node and resumes it with new input at exactly the point it paused, the closest analog found to "refine this specific part, don't restart."
- **Baton-pass, not call-and-return** — OpenAI Agents SDK handoffs (`openai.github.io/openai-agents-python/handoffs/`, official docs, fetched directly). A handoff is a tool the model calls to transfer control; "the new agent takes over the conversation... Handoffs stay within a single run." **Confirmed negative finding**: the fetched documentation describes no channel for the result to return to the delegating agent and no mechanism for it to judge sufficiency or ask for a refinement — this is a one-directional relay ("baton pass"), structurally unlike every call-and-return system above, not an unread gap (the doc page itself was fetched and asked directly about return/refinement).
- **Baton-pass, voluntary return by prompt convention, not framework guarantee** — Microsoft AutoGen AgentChat Swarm (`microsoft.github.io/autogen`, official docs + `_swarm_group_chat.py` source module + worked notebook example, all fetched directly, 2026-08-12 follow-up closing a self-flagged gap at the same rigor as the rest). Speaker selection: `for message in reversed(thread): if isinstance(message, HandoffMessage): self._current_speaker = message.target`; without a handoff, the same agent keeps the turn. **Confirmed**: "There is no automatic mechanism for control to return to a previously handoff-ing agent... No code path automatically reverts to an earlier speaker" — structurally baton-pass, same family as OpenAI Agents SDK. The nuance neither OpenAI's docs nor Anthropic's post show as explicitly: return *is* common in practice, but only because a given agent's own system prompt says to ("Always handoff back to planner when analysis is complete") and executes it as an ordinary `transfer_to_planner()` tool call — mechanically identical to any other handoff, not a distinct "return" API. **Confirmed gap**: the fetched worked example shows only forward/completion handoffs; no corrective-refinement handoff ("this part was insufficient, redo X") appears in the primary source read.
- **Delegation tool, return mechanism unreached** — CrewAI hierarchical process. `Delegate work to coworker(task: str, context: str, coworker: str)` and `Ask question to coworker(question: str, context: str, coworker: str)` tool signatures confirmed via official docs + search. **Explicit gap, not silently absorbed**: how the result returns, and how the delegating agent judges sufficiency, was not found in the documentation reached (official `docs.crewai.com/en/concepts/collaboration` page, fetched directly, does not state it) — flagged Unverified for this specific sub-question, not claimed absent from the actual source code (unreached, per Stage 2's "explicit report when a primary artifact is unreachable" — the source file implementing the tool was not located this session).

**Most frequent, and why**: not one converged pattern — two structurally different families, split by whether the orchestrator intends to stay in charge. **Call-and-return** (Claude Code subagent/resume, LangGraph supervisor + `Command`, and — already logged in Capability 5 — dsifry/metaswarm's producer/reviewer loop) keeps the orchestrator on the hook for synthesis and lets it re-invoke narrowly. **Baton-pass** (OpenAI Agents SDK handoffs) is cheaper per turn but structurally can't check or refine the specialist's output afterward unless a further handoff is defined back to the original agent. Which family a given system uses tracks a real design fork, not a maturity gradient — the OpenAI SDK's own docs frame handoffs as a *replacement* of control, not a delegation of a subtask.

**Trade-offs**: call-and-return costs a round trip and requires the orchestrator to hold synthesis logic; baton-pass is cheaper and simpler but gives up the orchestrator's ability to verify or refine after the fact; resume-with-full-history (Claude Code) is cheap continuity but risks the same anchoring Capability 5 already flags for reviewers; spawn-new-not-resume (Anthropic's own system) avoids anchoring and duplicate-context bloat but pays for it in duplicated *setup* work and, per Anthropic's own named failure mode, a real risk of duplicated *research* work between the old and new subagent if boundaries aren't drawn explicitly.

**Recurring anti-patterns / honest gaps**: judging "is this sufficient" by undocumented LLM discretion is the default in the two most production-grade systems found here (Claude Code's own delegation judgment, Anthropic's lead-agent synthesis) — a deterministic gate exists (Claude Code's hook + exit-code-2 mechanism) but is opt-in machinery layered on top, not the default anywhere found; vague, short task descriptions at handoff time is a named real failure (Anthropic's "research the semiconductor shortage" case) independently consistent with Capability 7/8's own finding that a Skill/task description's precision is what determines whether delegation works at all.

**Direct contradiction, logged rather than smoothed (per this skill's own review-loop discipline)**: Claude Code's resume mechanism is *designed* to hand a refining specialist back its full prior history "so it can pick up exactly where it stopped." Anthropic's own multi-agent research system deliberately does the opposite — spawn a fresh subagent rather than reopen the one that already ran. dsifry/metaswarm (Capability 5, already logged, High confidence) goes further still and makes *freshness mandatory* for one role (reviewer) while giving the *other* role (producer) persistent memory, on the explicit theory that continuity helps a builder and actively causes anchoring in a verifier. All three are deliberate, evidenced choices, not one right answer and two mistakes — the fork is **which role is being refined** (a continuing specialist vs. a judge re-checking that specialist's own prior work), not a disagreement about facts.

**What transfers to Engineer↔Researcher (ENGINEER repo ↔ AI Intelligence repo) and what doesn't**:
- **Transfers directly, already in practice**: a self-contained task contract with an explicit, pre-fixed sufficiency criterion (objective + output format + boundaries) — this is exactly `OPEN_QUESTIONS.md`'s own "criterion fixed before search" rule and is how this very investigation was briefed. No import needed; already converged on independently.
- **Closest real-world analog to the actual channel**: **cross-session messaging**, not subagent-resume. Engineer and Researcher are two separately-run Claude Code sessions/repos, not a parent session and its own subagent — the subagent-resume mechanism (`SendMessage` to an agent ID, full history retained automatically) requires both ends inside one session's tracked subagent tree (`~/.claude/projects/.../subagents/agent-{id}.jsonl`), which does not describe this pairing. The cross-session analog carries a real constraint worth naming plainly: **"never conversation history or files,"** plain text only, with a reply address — so a real "уточни X" follow-up between these two repos, if it followed this analog, would need to restate the necessary context each time rather than relying on an implicit shared history the way an in-session subagent resume can.
- **Transfers as a concept, not as ready machinery**: a deterministic (non-LLM) sufficiency gate before accepting "done" — Claude Code's own hook/exit-code-2 mechanism is harness-specific plumbing neither repo currently has an equivalent of; the transferable idea is narrower — that sufficiency-checking can be a checkable, code-level step and not only a model's self-report — not the specific hook API.
- **Does not transfer, and why**: CrewAI's coworker-delegation tool, OpenAI Agents SDK's handoff-as-control-transfer, and LangGraph's `Command`/graph-state primitives all assume a single shared orchestration runtime instantiating both agents as objects inside one process/framework. Engineer and Researcher are separate products (their own `CLAUDE.md`, persona, memory, repo) invoked as peers across a real process boundary — there is no shared runtime to place a `Command` object or a coworker-tool call into. Agent teams' shared task list and file-locked task-claiming has the same problem one level up: it assumes both agents are sessions under one local Claude Code installation sharing a team directory on the same filesystem, which the two separate repos are not shown to be.
- **Unresolved by this investigation, not decided here** (per the Responsibility Boundary Gate — this stays Research, not Design): whether a refinement re-invocation between Engineer and Researcher should resemble Claude-Code's "resume, keep full history" model or Anthropic's/metaswarm's "treat the re-ask as fresh, restate what's needed" model is exactly the fork the Direct Contradiction above describes, and this investigation deliberately does not pick a side — that choice belongs to a separate Design step, per `HOME.md`'s own instruction not to design the system ahead of the facts.

## Refinement to Capability 4 (Permissions) — first-person, self-referential finding

While running the parallel subagent batch above, the coordinating process itself hit the exact class of problem Capability 4 already documents: per-call permission prompts (e.g., for `WebFetch`/`api.github.com`) interrupt a human who becomes forced middleware the moment more than one agent is fetching from the same domain concurrently. **Failure Mode (logged, per the self-referential discipline this project applies to every other object)**: research is repeatedly interrupted by per-file/per-domain Permission Prompts, turning the human into request-approval middleware for work that was supposed to run autonomously in the background.

**Fix, as a standing working practice**: before dispatching parallel subagents, enumerate which domains/tools they will collectively need and request session-scoped permission for the whole set once, rather than letting each subagent's first call surface its own prompt.

**New quality criterion for this skill's own output**: good research is not judged only by its conclusions (the existing Definition of Done, which judges the *object* investigated, not the process running the investigation) — the *amount of manual human involvement required during execution* is itself a measurable property of a good research process, alongside it.

## Refinement to Capability 4 (Permissions) — Capability Layering: available / belongs / permitted / recommended (2026-08-12)

**Source**: direct question from Engineer (sibling Foundation repo, ENGINEER), relayed from a registered `ENGINEER/OPEN_QUESTIONS.md` question (2026-08-12, "Как зрелые системы различают «доступно среде» / «принадлежит агенту» / «разрешено агенту» / «рекомендовано для задачи»"). Triggered by a real case: Engineer's `skills/tool-selection/SKILL.md` claimed Exa/Firecrawl/Context7 "don't belong to Engineer, don't assume availability," but `claude mcp list` showed all three connected and callable in the live session — the rule conflated "connected right now" with "owned by/permitted to/recommended for" the agent. Internal-context-first rule applied: `ENGINEER/skills/tool-selection/SKILL.md`, its `evidence.json`, and `ENGINEER/OPEN_QUESTIONS.md`'s own fixed answer-criterion read in full before external search opened.

**Two systems clear the brief's bar (≥3 of 4 layers, mechanism-level, not just named) — plus supplementary partial evidence from two more.**

### System 1 — Claude Code / Claude Agent ecosystem (Confirmed, all 4 layers, official docs fetched directly this session, version-numbered)

- **Available in session/environment** — MCP servers connect at one of three *scopes*, and `claude mcp list`/`claude mcp get <name>` reports connection status (`✔ Connected`, `⏸ Pending approval`, `✘ Rejected`) **regardless of which scope produced the connection** (`code.claude.com/docs/en/mcp`, "MCP installation scopes" + "Managing your servers"). A tool being visible/callable in the running session is a fact about the session, not about ownership.
- **Belongs to agent** — two independent, separately-documented mechanisms, both literally answering "whose is this":
  - *Repo/project ownership*: **project scope** stores the server in `.mcp.json` at the project root, checked into version control, "shared with everyone in the project" — this is what travels with `git clone`. **Local** and **user** scope store the same-looking connection in `~/.claude.json` (home directory, outside the repo) and are explicitly "private to you," not shared with the team and not in version control. This is the exact mechanism behind Engineer's own finding: ENGINEER has no `.mcp.json` (confirmed in Engineer's own diary), so Exa/Firecrawl/Context7 being visible in `claude mcp list` proves only that a local- or user-scoped connection exists on this machine/session — not that the ENGINEER repo owns them.
  - *Subagent ownership*: a subagent definition's `tools`/`disallowedTools`/`mcpServers` YAML frontmatter fields (`code.claude.com/docs/en/sub-agents`) explicitly scope which tools and which MCP servers belong to *that* subagent, separate from the main session's pool — an inline `mcpServers` entry in a subagent's frontmatter can even connect a server "to keep [it] out of the main conversation entirely," i.e. a server can belong to one subagent and be invisible everywhere else in the same session.
- **Permitted (technical allow/ask/deny)** — `settings.json`'s `permissions.allow`/`ask`/`deny`, evaluated deny→ask→allow, first match wins regardless of specificity (`code.claude.com/docs/en/permissions`); MCP-specific rule syntax `mcp__<server>` / `mcp__<server>__<tool>` / `mcp__*` (deny-only wildcard); managed-settings `allowedMcpServers`/`deniedMcpServers` policies and `allowManagedMcpServersOnly`; per-connector org control forcing `ask` regardless of local allow rules; MCP tools flagged `requiresUserInteraction`. This is a **distinct configuration surface** from ownership above — a server can belong to the project's `.mcp.json` and still be denied by `settings.json`, and vice versa a locally-owned server can be freely permitted.
- **Recommended for a specific task, not any task** — two separate, confirmed mechanisms, both advisory rather than enforced:
  - A Skill's or subagent's `description` frontmatter field is the artifact Claude's own runtime uses to decide *when* to delegate/invoke it ("Claude uses each subagent's description to decide when to delegate tasks" / a Skill's description drives automatic activation) — this is model-mediated judgment, not a deterministic rule, and is explicitly a different field from `tools`/`mcpServers` (ownership) and from `permissions.allow` (technical permission).
  - MCP tool **annotations** (`readOnlyHint`, `destructiveHint`, etc., `modelcontextprotocol.io/specification/.../server/tools`) are explicitly *hints*: "clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers" — the spec itself draws the available/permitted vs. recommended line: an annotation may say a tool is safe/preferred for a given operation, but that claim carries no permission weight and must not be used for security decisions.
  - Also confirmed, task-scoped rather than session-scoped: a Skill's `allowed-tools` frontmatter field pre-approves specific tool-call patterns **only while that skill is active**, and the grant "clears when you send your next message" (`code.claude.com/docs/en/skills`) — this sits between layers 3 and 4: it is a real permission grant, but one deliberately bound to *this* task's invocation window, not the session as a whole.

### System 2 — LangChain / LangGraph agent middleware (Confirmed for 3 of 4 layers, official `docs.langchain.com` page fetched directly)

- **Available in environment** — `langchain_community.agent_toolkits` ships importable, pre-built tool collections ("Toolkits") that exist in the codebase independent of any agent; `get_all_tool_names()` enumerates what could be loaded.
- **Belongs to agent** — a specific `Agent`/chat model is given tools explicitly via `tools=[...]` at construction, or via `bind_tools()` on the model — an available toolkit tool is not usable by a given agent until named in that agent's own list.
- **Permitted (technical allow/ask/deny)** — `HumanInTheLoopMiddleware(interrupt_on={...})` is a **separate policy dict keyed by tool name**, layered on top of the `tools=[...]` ownership list, not folded into it: `{"write_file": True, "execute_sql": {"allowed_decisions": [...]}, "read_data": False}` — `False` auto-approves, a config or `True` pauses for a human `approve`/`edit`/`reject`/`respond` decision via `interrupt()`, persisted through a checkpointer so the graph can resume exactly where it paused. Confirmed directly against `docs.langchain.com/oss/python/langchain/human-in-the-loop`, including a verbatim code example.
- **Recommended for a specific task** — **not found** in this system. No structured field distinct from ownership/permission was located; task-appropriateness is left to the model's own prompt-level reasoning. Reported honestly as a gap in this system, not assumed present because Claude Code has one.

### Supplementary, partial evidence (does not independently clear the ≥3-of-4 bar, but corroborates that "belongs" and "permitted" are kept as separate surfaces across unrelated vendors)

- **OpenAI Agents SDK** (`openai.github.io/openai-agents-python/tools/`, `/guardrails/`, fetched directly) — confirms **belongs** (`Agent(tools=[...])`) and **permitted** as two separate, independently-confirmed sub-mechanisms: `allowed_callers` (per-tool, `["direct"]`/`["programmatic"]`/both — governs *how* a tool may be invoked) and, separately, `Agent.as_tool(..., needs_approval=...)` (a pause/resume human-approval gate, distinct from `allowed_callers` — "`allowed_callers` is about access method; approval is about gating execution"). **Available-vs-belongs does not separate cleanly here**: even OpenAI's own "hosted tools" (`WebSearchTool`, `FileSearchTool`) require the same explicit `tools=[...]` declaration as a user-defined function tool — there is no session-level "connected but not yet claimed" state the way an MCP server scope produces in Claude Code. **Recommended-for-task: not found**, same gap as LangGraph.
- **Amazon Bedrock Agents (Classic)** (`docs.aws.amazon.com/bedrock/latest/userguide/agents-permissions.html`, `agents-action-create.html`, fetched directly) — confirms **belongs** (an Action Group is attached to one specific agent; the Lambda function's own resource-based policy is conditioned on `AWS:SourceArn: arn:aws:bedrock:...:agent/{agent-id}`, i.e. the Lambda is only invokable *by that one agent's ARN*, not by "any Bedrock agent in the account") and **permitted**, as two independently-enforced IAM layers: the agent's own identity-based service-role policy (what the agent's role may call) and the Lambda's resource-based policy (who may call the Lambda) — a true separation of "the agent is allowed to act" from "this specific resource accepts being acted on." **Flagged honestly**: AWS's own docs state Bedrock Agents Classic "is no longer open to new customers" (superseded by Bedrock AgentCore) — real and checkable, but a legacy surface, not current best practice. Available and recommended-for-task layers not clearly separated in what was reached this session.
- **Salesforce Agentforce** — attempted (Topics/Actions/permission-set architecture looked promising for a fourth, non-code-harness vendor), but the two most relevant official Help Center pages (`copilot_topics_actions.htm`, `agent_user.htm`) returned 404s or unrenderable content when fetched directly this session. ## Refinement — Automatic Capability/Model Selection: Skills, Tools/MCP, Models, Cost (2026-08-12)

**Source**: second direct question from Engineer, same day as the Orchestrator↔Specialist investigation above, re: a 4-layer "Capability System" (Skills / Tools-MCP-Plugins / Models / Routing). Explicit trigger case named in the brief: a physically-connected tool (Exa) that a rule forbade *considering*, so it was never used despite being reachable — the gap under investigation is "has access" vs. "knows to consider and choose," not access itself. Full evidence, sources, and per-sub-question breakdown: `knowledge/evidence/2026-08-12-capability-model-routing-selection.md`. Eight sub-questions, criterion fixed before search per `OPEN_QUESTIONS.md`.

**Findings, by capability layer**:

- **Capability discovery** (extends Capability 8): Anthropic's tool search tool (`tool_search_tool_bm25_20251119`/`_regex_20251119`, GA, official docs fetched directly) — tools marked `defer_loading: true` are excluded from context until the model itself searches for them; a search returns up to 5 `tool_reference` blocks, auto-expanded into full definitions. Measured: >85% token reduction for a typical 5-MCP-server setup (~55k tokens → 3-5 tools' worth), and an explicit, vendor-stated accuracy cliff — tool-selection accuracy measurably degrades past roughly 30-50 available tools without this mechanism. Distinct from the **MCP Registry** (`server.json` at a well-known path, official registry launched 2025-09-08), which is publish/operator-time discovery of *what could be connected at all* — no mechanism found in this batch lets a running agent autonomously connect a new, not-yet-installed capability mid-task; that step stayed human in every source checked.
- **Tool selection among available tools**: BM25/regex keyword-style ranking (Anthropic) and embedding-similarity-to-labeled-task-vectors (Red Hat/CNCF's LLM Semantic Router, BERT-based, fetched directly) are two independently-arrived-at mechanisms solving the same class of problem for two different capability types (tools vs. models) — corroborating that "rank candidates, load only the top few" generalizes across the tool/model boundary, not tool-specific.
- **Model selection per subtask**: the one confirmed-automatic, learned, per-message model router found is **single-vendor** — OpenAI's GPT-5 router (fast vs. deep-reasoning model, retrained continuously on real usage signals: user-initiated switches, preference rates, measured correctness; Medium confidence — direct fetch blocked, WebSearch-aggregated). Every **cross-vendor** case found (Claude implements / Codex reviews — several practitioner write-ups) is a human-designed, static, one-time pipeline choice, not a runtime policy that itself decides which vendor handles which subtask. **This is an explicit, load-bearing gap, not a smoothed-over guess**: automatic per-subtask model selection is demonstrated within one vendor's own model family; it is not demonstrated across vendors (Claude/Gemini/Codex/other) in any production system found this session.
- **Cost optimization, paired with a quality claim, not cost alone**: cascade-with-confidence-threshold (FrugalGPT) and pre-classification threshold routing (RouteLLM, ICLR 2025) both frame themselves explicitly as *quality-preserving* cost reduction (RouteLLM: 85% cost cut at 95% retained quality; FrugalGPT: up to 98% cost cut "with the same output quality") — directly matching the "cheapest mechanism that keeps sufficient quality, not just cheapest" framing in the brief, not "always cheapest." Programmatic tool calling (Anthropic, official docs) is the one mechanism in this batch with a *paired* accuracy-and-cost number in the same benchmark (+11% task performance, -24% input tokens on BrowseComp/DeepSearchQA; -38% billed input tokens with no accuracy change on a 75-tool PM-agent benchmark) rather than a cost number alone. Prompt caching (50-90% discount on cached input-token prefixes) and semantic caching (20-45% hit rate typical, up to 67-76% in specific cited deployments) are complementary, not competing, layers.
- **Verification that a capability was actually used and gave a result**: structured trace assertions (Langfuse/LangSmith — tool calls recorded as structured fields, distinguishable from an LLM-judge "groundedness" rating of whether the result was actually fit for the request) plus a real, already-logged instance in this project's own knowledge (`External Validation` section above): Anthropic's own automated LLM-judge eval passed a version of their research pipeline that was, in fact, choosing SEO content farms over academic sources — only human evaluators caught it. **No fully automatic, human-calibration-free verification mechanism was found anywhere in this batch** — every one reduces the volume of cases needing human review, none was found to eliminate that step.
- **Updating capabilities as newer variants appear**: vendor-driven lifecycle states (Anthropic's Active/Legacy/Deprecated/Retired) are a publish-side signal, not a consumption-side automatic switch. One single-practitioner mechanism (joost.blog, fetched directly) auto-pulls Skill updates from a repo's `main` branch on every session start with zero human approval — explicitly trading a review gate for currency, hobby-scale evidence only.

**Reinforcement (same day, coordinator-relayed real trigger — Engineer's own session growing heavier under parallel background agents) — fan-out cost, sub-question 5**: the vendor-recommended and independently-benchmarked answer to "cheap parallel workers without losing quality" is role-based model tiering, not blanket cheap-everywhere — an expensive model kept on orchestration/judgment (decomposition, synthesis, verification, stopping decisions), cheaper models on bounded execution. Anthropic's own multi-agent research system (previously logged) already recommends exactly this split; a third-party benchmark (Arize AI, fetched directly) puts a number on it — a cheap-executor team supervised by an expensive orchestrator retained 96% of an all-expensive team's benchmark score at 46% of the cost — with an explicit, named floor: "cheap executors don't mean you can cheap out on the orchestrator," since a cheaper model swapped into the judgment role measurably doubled hallucination rate in the same source's cited case. Claude Code's own official cost docs (fetched directly, Confirmed) show this tiering is real but **manual**: a subagent must be explicitly pinned to a cheaper model (`model: haiku`); left unset, it inherits the parent's (often more expensive) model by default — confirmed by a real, filed product complaint (`anthropics/claude-code` issue #26179) asking for the opposite default. The two mechanisms found to run with zero configuration at all are prompt caching and auto-compaction; every cost control beyond that (spend caps, TPM/RPM limits, per-role model pinning, usage-attribution dashboards) requires a human to set it. **A named counter-finding qualifies fan-out itself, not just its cost**: an independent, self-critical benchmark (`systima.ai`, "The Subagent Tax," fetched directly) found Claude Code subagent fan-out cost 2.6x-5.9x the input tokens of sequential execution on the same task and was **not faster on any task measured** — the real payoff of fan-out in that benchmark was context isolation, not speed or cost, a different justification than the one usually advertised for building it.

**Reinforcement (same day) — periodic capability retirement, sub-question 7**: the owner's own distinction — "current and right-sized" vs. "maximum coverage installed" — has real, shipped tooling behind it, not just a stated preference. `mcp-audit` (a real Claude Code Skill, fetched directly) classifies connected MCP servers as KEEP/DISABLE/REVIEW using usage recency (7+ days idle) and token-overhead heuristics, with named minimality targets (under 10 servers, under 80 tools) and a hard rule that removal always requires human confirmation. `deadskills`/`skillreaper` do the same at the Skill layer using local transcript evidence, one report-only, one offering reversible quarantine-and-restore. **Honest gap, explicitly checked and not found**: none of these tools, nor the closest general-software analog checked directly (Dependabot/Renovate-style automated dependency-freshness bots, which were not found applied to AI-agent capability inventories anywhere in this search), run on a recurring *schedule* — every real mechanism found is manually invoked or triggered by a felt symptom ("sessions feel slow"), not calendar-driven. The retirement *mechanism* (usage-evidence classification, human-approved, reversible-by-default) is real and non-hypothetical; a standing periodic *cadence* for running it is the part this investigation could not confirm exists anywhere in production.

**Direct contradiction, logged rather than smoothed**: that same auto-pull practice (no human gate, trust `main`) sits next to independent, separately-sourced practitioner guidance that **a new model release should trigger a manual retest of every Skill**, because a Skill that behaves correctly on one model can behave differently on the next. Neither source addresses the other's concern — auto-pulling new Skill *content* says nothing about whether that content still behaves correctly on whatever model happens to be active when it's pulled. This is the same family of tension as the "silent quality regression" risk independently named by production-routing write-ups (a request routed to a cheaper model can produce a subtly worse answer with no dashboard signal) — several sources in this batch actively warn against reaching for routing/caching/auto-update machinery before the cost or latency pain is real (one names a rough $500/month LLM-spend floor below which routing infrastructure isn't worth its own complexity), a direct echo of this map's own existing Capability 11 (Restraint / Scope Discipline) applied to this specific layer, not a new principle.

**Cross-reference to existing Capability 4 (Permissions)**: the brief's own triggering case — a connected-but-forbidden-to-consider tool — maps directly onto this map's already-logged finding that a bare-tool-name **deny removes the tool from the model's context entirely**, as opposed to a scoped deny that leaves it visible but blocks the call. That distinction (already triangulated five ways in Capability 4, before this session) is the closest existing external mechanism match to "must not even consider," found again rather than newly discovered — logged here as a cross-reference, not a new mechanism, per this map's own practice of noting when two capabilities share a substrate.

**Evidence level**: Confirmed (Anthropic tool-search-tool, programmatic-tool-calling, and Claude Code cost-management docs — all official, fetched directly, full page) · Established/Medium (RouteLLM, FrugalGPT, GPT-5 router, Langfuse/LangSmith, MCP Registry — WebSearch-aggregated, not independently re-fetched from the primary artifact this session) · Established/Medium, directly fetched (Red Hat/CNCF LLM Semantic Router, joost.blog, Arize AI, Systima "Subagent Tax," `mcp-audit` SKILL.md, Deadskills/Skillreaper comparison) · Unverified/gap, stated explicitly (fully-automatic cross-vendor model-per-subtask routing; fully human-calibration-free verification; a scheduled/periodic — as opposed to manual/symptom-triggered — capability-retirement cadence).

## Refinement — Cross-Repo Status Sync (git/markdown, no CI, no shared backend), 2026-08-17

**Source**: direct brief from Engineer, prompted by a real found-and-fixed rassinhron between `ENGINEER`'s and this project's own `DECISIONS.md`/status records on the same question (one said "Locked," the other "Proposal"). Full source-level detail: `knowledge/evidence/2026-08-17-cross-repo-status-sync-patterns.md`. Criterion fixed before search per Engineer: minimum 2 real, sourced patterns, each with an applicability verdict (use as-is/adapt/merge/defer/reject) for a git-only markdown system with no CI — explicitly excluding priority-between-patterns or where-to-implement, which stays Engineer's/the owner's decision.

**Patterns found**:
- **Git submodule as commit-SHA pointer, not copy** — a gitlink references one exact commit in another repo rather than restating its content; drift becomes visible as an explicit out-of-date pointer (`git status`/`git diff`) rather than a silently-typed contradiction between two independent prose statements. **Adapt**: literal submoduling is heavier structural coupling than two peer repos likely want, but the underlying idea — pin a status to a verifiable commit reference instead of a restated word — is usable without the submodule machinery itself.
- **ADR "superseded by" bidirectional link + Richards & Ford's centralization rule** (Nygard's ADR status field; Richards & Ford, *Fundamentals of Software Architecture*, quoted via `synchronium.github.io/software-architecture-wiki`: cross-application/enterprise-level decisions belong in one shared, universally-accessible location, not per-repo copies). **Use as-is** for the bidirectional-link half (cheap, already convention-adjacent to this project's own `OPEN_QUESTIONS.md` reclassification rule) — but that half only makes a single repo's own record self-honest about its history, it does not by itself stop two repos from independently drifting. **Adapt** for the centralization half — the transferable idea (one canonical location per cross-cutting decision, other repos reference rather than re-type) without the literal shared-wiki mechanism neither repo currently has.
- **shields.io dynamic endpoint badge** (official docs) — a live-pull, zero-CI mechanism: the consuming repo stores no status text at all, only a reference that's fetched fresh from the canonical repo's raw JSON at every render. **Reject** for this specific pairing, and this is the useful negative finding: it only resolves drift for a *human viewing rendered markdown in a browser*, not for the actual readers here — Engineer and Researcher parsing raw file text as agents, where a rendered image's live value is invisible. Its one transferable idea ("compute from the canonical source, don't write a static copy") duplicates what the submodule pattern already captures, so it adds no new adaptable substance once that one is logged.

**Honest gaps, not smoothed over**: a TC39 `proposals`-repo central-registry candidate pattern (individual proposal repos vs. one central stage-tracking repo) was investigated and dropped — the actual sync mechanism between the two was not confirmed in the pages fetched directly this session (`tc39/proposals/README.md`, `tc39/how-we-work/README.md`), so it is not counted as evidence rather than assumed to work a particular way.

## Refinement — Professional vs. superficial business diagnosis: behavioral character (2026-08-17)

**Source**: task_id `ENG-2026-08-17-BIZPRODUCER-003`, direct call from Engineer. Four sources triangulated across three distinct genres (structured consulting method, accelerator validation discipline, advisor-client relationship), converging on the same underlying shape even though none cites the others: **treat an assumption as an assumption until it is tested against a fact, and say so out loud when a conclusion is less than certain.**

- **McKinsey** (primary, full podcast transcript fetched directly) — problem definition is checked, never assumed, before any analysis starts; prioritize what is both important *and* changeable, not just important; match plan depth to the stakes (a 50-page/3-month plan is named as a failure, not rigor); two specific named biases are checked for by process, not personality (availability bias, hierarchy/"sunflower" bias); every conclusion states its own confidence and conditions instead of flat certainty ("this is a likely answer under the following conditions," not "this is the answer" — Sarrazin, verbatim); a model/algorithm is never a substitute for correct problem definition.
- **Y Combinator Startup Playbook** (primary, fetched directly) — a claim about the business is tested against a concrete artifact (a letter of intent, a launch), not asserted; what people say and what people do are tracked as two separate signals, never merged into one; a forced, conviction-less diagnosis is a named, specific failure pattern ("all of them failed... plausible sounding but derivative").
- **The Mom Test** (Established, 3-way convergent secondary) — opinions and hypotheticals about the future are excluded as evidence by construction, not because people lie maliciously but because the question format itself produces false-positive validation; the substitute is always a question about specific already-happened behavior; a stated intention isn't counted until it costs the person something.
- **The Trusted Advisor** (Established, 3-way convergent secondary) — the advisor's job is named explicitly as "useful," not "right" or "liked" (a blunt, accurate diagnosis delivered without care for how it lands is also a failure, not a virtue by itself); sometimes the correct diagnosis is "you don't need this," and that costs trust to say, not gains it for free.

## Refinement — Unattended/headless agent autonomy: sandboxing, non-interactive config, post-hoc audit (2026-08-18)

**Source**: Engineer's direct brief, registered `ENGINEER/OPEN_QUESTIONS.md` (2026-08-18 entry), criterion fixed before search. Context named explicitly in the brief: the owner had already, same day, rejected `--dangerously-skip-permissions` as a blanket solution (`ENGINEER/DECISIONS.md`, 2026-08-18) — this investigation does not reopen that, it answers the harder question of what production systems actually do instead of a single bypass flag. **Sandboxing (2 systems, both primary-source-confirmed)**: Claude Code exposes six distinct isolation layers (built-in Bash sandbox, a beta `sandbox-runtime` package wrapping the whole process in Seatbelt/bubblewrap, dev container with default-deny iptables firewall, custom container, VM, and an Anthropic-hosted web VM) — each documented with its own threat model and setup cost, not a single on/off switch. OpenAI Codex CLI takes a materially different design: OS-level sandboxing (Seatbelt on macOS, Landlock+seccomp on Linux) is **on by default without requiring Docker at all** — isolation is a property of the process, not of a container, which is the opposite default from every other system checked. Honest gap: neither of Claude Code's non-Docker isolation layers (Bash sandbox, sandbox-runtime) supports native Windows — both require WSL2 or a container/VM instead, a materially relevant limit for a Windows-native host.

**Non-interactive config, and what actually backs its safety (3 systems, the core of this refinement)**: the field's real answer to "how do you remove the approval prompt safely" is never "just remove it" — it is always a second, independent mechanism substituted in its place, and it takes one of three concrete forms found:
- **A second model reviewing actions** — Claude Code's `auto` permission mode routes every non-trivial action through a separate classifier model (Sonnet 5 by default, independent of the session's own model) before it executes, with a versioned, growing, publicly documented list of what it blocks unconditionally (force push, `curl | bash`, self-approving one's own PR, production deploys, secret exfiltration, and dozens more, each dated by the Claude Code version that added it) — and the classifier is fed only user messages, tool calls, and CLAUDE.md, with tool *results* stripped specifically so hostile content read from a file or webpage cannot manipulate the reviewer directly.
- **Two independent technical/policy axes** — OpenAI Codex CLI names this explicitly: `sandbox_mode` ("what Codex can do technically") and `approval_policy` ("when Codex must ask you") are documented as two separate layers that compose, not one setting. Setting `approval_policy=never` is safe specifically because `sandbox_mode` still enforces a hard technical boundary regardless of what the policy allows — the same structural idea as Claude Code's isolation-boundary guidance, independently reached by a different vendor.
- **Containment alone, with an explicit warning about what happens without it** — AutoGen's `human_input_mode="NEVER"` removes the human-input pause but is not itself a safety mechanism; AutoGen's own docs warn that its local executor "will run code on your local system, use it with caution," and the only thing that makes `NEVER` safe is a deliberate choice to swap in `DockerCommandLineCodeExecutor`. Unlike Claude Code (a classifier) or Codex (a named dual-layer contract), AutoGen has no separate reviewing mechanism at all — container isolation is the entire safety story, and it is opt-in, not structural.

**Post-hoc audit/provenance (2 systems, plus one same-vendor addendum)**: GitHub Copilot's coding agent combines three things into one gate rather than treating logging as passive record-keeping — every commit is signed/attributed, every commit message links to the full session log ("for auditing purposes," stated as the log's explicit purpose), and the person who triggered the agent is *structurally prevented* from approving its own resulting PR, which converts the audit trail from optional reading into a mandatory checkpoint. AWS Bedrock AgentCore logs every agent invocation as a CloudTrail event at the platform layer, independent of the agent itself — the agent cannot omit or edit its own record because it isn't the one writing it — but this requires AWS account infrastructure with no equivalent in a plain git-repo environment. Same-vendor addendum, new this session: Claude Code's classifier performs a *third* check specifically after a subagent finishes — reviewing its full action history and prepending a security warning to the result if anything looks wrong, explicitly marking the result "unreviewed and should be treated as untrusted" if the check itself fails to run. This is a genuine post-hoc mechanism distinct from the EXECREC batch's finding (2026-08-12, session JSONL as a retrievable record) — that batch answered "can a creator retrieve what an independent agent did," this answers "does anything re-examine what it did without being asked."

**What transfers to Engineer's own environment, and what doesn't, stated per finding (not designed here — Research only, per `MISSION.md`)**:
- Claude Code's `auto` mode and `dontAsk` mode are not hypothetical — they are features of the exact same Claude Code the owner already runs, requiring no new infrastructure. Whether `auto` is already the owner's active mode depends on the Claude plan in use, which this investigation did not check — named as [UNKNOWN], not assumed.
- The GitHub Copilot "triggering user cannot approve their own PR" pattern is not a new idea to import — it is an independent, external confirmation that a pattern the owner is *already running manually today* (Engineer prepares and commits, the owner alone pushes, documented repeatedly in `ENGINEER/DECISIONS.md` 2026-08-18) is a real production audit-gate mechanism, not an ad hoc invention specific to this project.

This is named as a gap, not filled in by this investigation.

**Принцип ранжирования по срочности — адаптирован, не заимствован целиком**: установленный 3-факторный механизм FMEA/Risk-Priority-Number (Severity × Occurrence × Detectability, происхождение AIAG & VDA/MIL-STD-1629, самоавторизующий перемасштабирование по собственной литературе) рекомендуется вместо более простой, более распространённой 2-факторной риск-матрицы Severity×Likelihood (собственное руководство ICAO по Safety Risk Management, кросс-отраслевой стандарт), именно потому что третий фактор — переименованный в **Тишину** (узнает ли владелица сама, или только после того, как клиент уже ушёл/пожаловался) — улавливает единственный самый значимый тип сбоя в бизнесе, построенном на личных отношениях с клиентом: *тихий* дефицит против *видимого*, идентичные по серьёзности и частоте, но очень разные по реальной срочности. Собственная шкала 1–10 из инженерной литературы сжата до 1–3 (Низкий/Средний/Высокий) по фактору, диапазон RPN 1–27 — исходная литература явно разрешает такое перемасштабирование; полная инженерная шкала построена для команд, оценивающих сотни технических типов сбоев с инструментальной точностью, не для первого прохода одного владельца по компании.
