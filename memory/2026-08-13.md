## Прямой вызов Engineer → Researcher: три механизма из ревизии старого MAIN_ENGINEER — реальная практика или изобретение одной сессии

Бриф от Engineer, вопрос зарегистрирован в `ENGINEER/OPEN_QUESTIONS.md` (2026-08-13): в ходе инженерной ревизии старого предшественника Engineer (`github.com/megapolisagent/MAIN_ENGINEER`, публичный репозиторий) найдены три сильных механизма. Задача — не спроектировать что-то новое, а проверить, реальная ли это мировая практика, прежде чем считать их переносимым решением, и явно назвать, если старый репозиторий цитирует авторитет (Карпати/Anthropic) не в точном соответствии с тем, что тот источник реально говорит.

Первым делом прочитан сам первичный артефакт напрямую (`raw.githubusercontent.com`, девять файлов старого репозитория, полный текст, не по памяти) — дисциплина Stage 2 требует этого до любого вывода. Карпати не найден ни в одном из девяти прочитанных файлов — честно зафиксировано как непроверенная предпосылка брифа, не как «опровергнуто» (в репозитории есть ещё непрочитанные файлы: `registry.md`, один из четырёх `external_review`, `ARCHIVE/`, `PROJECT_SUMMARIES/`). Зато нашлась реальная, не связанная с тройкой из брифа, но точная в рамках самого запроса на проверку атрибуции находка: `SKILLS_REGISTRY.md` называет «правилом Anthropic» требование трёхслойной структуры Skill с обязательной папкой `tools/» — прямая проверка официальной документации Anthropic (`anthropics/skills` README + `best-practices` страница, обе получены напрямую) показала, что настоящее требование Anthropic — только два поля фронтматтера (`name`/`description`), без обязательной `tools/`. Атрибуция не совпадает с первоисточником — названо прямо, не смягчено.

По трём механизмам, каждый сверен против внешней практики отдельно:

1. **Симметричная межагентная калибровка + Tier-модель права записи через «External Review Package»** — не найдено. Частичные, не совпадающие по всем осям аналоги существуют (централизованно навязанный tiered RBAC в enterprise multi-agent governance, arxiv.org/pdf/2605.10223; самоправящаяся «конституция» через GitHub PR с внутренними ролями reviewer/auditor, `Gamferno/agent-constitution`), но ни один не совпадает с полной комбинацией старого MAIN_ENGINEER (симметричные равноправные агенты + предложение по факту сессии + самоинтеграция целью, не прямая правка + тир по классу изменения). Честное «не найдено», не «похоже, наверное есть».
2. **«Business/usage Loop > Engineering Loop»** — подтверждает опасение самого брифа. Общий предок реален и хорошо подтверждён (Lean Startup Build-Measure-Learn; a16z/Sequoia про retention-first именно для AI-продуктов), но как отдельная, именно AI-agent-специфичная документированная практика реальной компании, эксплуатирующей продакшн-агентов — не найдено. Старый MAIN_ENGINEER записал общий стартап-принцип в CORE-файл как если бы это была AI-agent-специфичная норма, без такой проверки.
3. **Паспорт-заголовок + порог ~300 строк + Major.Minor.Patch версионирование для файлов, которые читает и по которым действует агент** — смешанный, точный, не округленный в одну сторону результат. Порог длины → разделение файла подтверждён самой сильной возможной парой источников (официальная и актуальная документация Anthropic по авторству Skills) — но настоящее число Anthropic — 500 строк, не ~300 (не атрибуционная ошибка: старый репозиторий не ссылается на Anthropic за этим числом, просто оба независимо оказались в одной окрестности). Major.Minor.Patch именно для файлов промптов/конфигурации агента — подтверждено сходящейся практикой нескольких независимых источников (Arthur.ai, Latitude, Agenta, aiquinta, tianpan.co). Сам паспорт-заголовок как обязательный блок фронтматтера внутри файла — не подтверждён и не опровергнут: спека Anthropic требует только два поля, ближайший реальный аналог (метаданные версии в отдельном слое управления, не в самом файле) — другая по форме практика.

Не принято ни одного дизайн-решения для Engineer/ENGINEER — граница Craft/Engineering выдержана, это чистая проверка «реальность против рёбра одной сессии», не рекомендация внедрять или не внедрять.

## Второй прямой вызов Engineer → Researcher того же дня: Kimi (Moonshot AI) — реальная сила/цена, допустимые данные, место в выборе модели

Бриф от Engineer, вопрос зарегистрирован в `ENGINEER/OPEN_QUESTIONS.md` (2026-08-13, второй записью). Найдено на практике (ревизия старого AI_OS): Kimi K3 числилась предпочтительной для >200K-токенных объёмов, дешевле Gemini, но без внутренних/конфиденциальных данных — юрисдикция китайская, формулировку сам AI_OS не проверял. Явное требование: проверить пункт про юрисдикцию самостоятельно, не принимать формулировку как факт.

По всем четырём пунктам — прямой fetch первоисточников, не по памяти:

1. **Цена/контекст/бенчмарк** — подтверждено настоящими цифрами с обеих сторон, не только «звучит разумно». Официальная цена Kimi K3 (`platform.kimi.ai`, `forum.moonshot.ai`, оба получены напрямую) — $3.00/$15.00 за MTok (1M контекст, $0.30 при кэш-хите) — реально дешевле собственного длинноконтекстного тарифа Gemini выше 200K токенов ($4.00/$18.00, агрегировано по поиску). Независимый агрегатор бенчмарков (Artificial Analysis, получен напрямую) ставит Kimi K2.6 выше Gemini 2.5 Pro по Intelligence Index (45 vs 26) и дешевле за токен; отдельно — Kimi K2.6 обгоняет GPT-5.4/Claude Opus 4.6/Gemini 3.1 Pro на SWE-Bench Pro (58.6%) — редкий и сильный результат, не смягчённый до «сопоставим».
2. **Где реально подходит** — агентный кодинг, длинный контекст, tool-use/поисковые задачи (BrowseComp/DeepSearchQA) — по не только маркетинговым источникам, с честной оговоркой, что вне этих трёх кластеров ничего не проверялось.
3. **Юрисдикция/данные** — расщеплено на два слоя, которые формулировка AI_OS слила в один. Официальная политика (получена напрямую) — хранение в Сингапуре, сингапурское юрлицо, без opt-out на обучение. Отдельно и независимо подтверждено (Wikipedia + South China Morning Post, две сходящиеся независимые статьи) — сама компания китайская, штаб-квартира в Пекине, основана выпускником Tsinghua/CMU/Meta/Google, финансируется Alibaba/Tencent/Meituan/китайскими госфондами — это реально подтверждённый факт, отдельный от текста политики. А вот конкретное дальнейшее утверждение, что инференс технически идёт через пекинскую инфраструктуру — держится на ровно одном источнике, который сам же в своей верификационной странице честно называет точную локацию датацентров непроверенной. Не смягчено ни в «подтверждено», ни в «опровергнуто» — instinct AI_OS не выдуман, но был подан как решённый механизм, когда решён только корпоративный слой.
4. **Технический вызов из Claude Code** — да, два разных реальных пути, не один: (а) официальный, задокументированный Moonshot Anthropic-совместимый endpoint (`api.moonshot.ai/anthropic`) — но это замена всей CLI-сессии целиком, не выбор на уровне подзадачи, и WebFetch через него не работает; (б) неофициальные сторонние MCP-мосты (`kimi-api-mcp`, `x51xxx/kimi-mcp-server`) к собственному REST API Moonshot — именно то, что нужно для делегирования одной подзадачи при оркестраторе на Claude, но не встроено, требует отдельного API-ключа, не установлено ни у Researcher, ни у Engineer.

Не принято дизайн-решений для Engineer — граница Craft/Engineering выдержана.
