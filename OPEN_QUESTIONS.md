# Реестр открытых вопросов

> Не то же самое, что решение. Решение — выбор среди альтернатив, который утверждает владелец явным словом (см. `DECISIONS.md`). Открытый вопрос — пробел в знании, который закрывается доказательством, а не одобрением.

## Когда здесь появляется запись

Не для всего подряд — только для вопроса, который нельзя закрыть прямо сейчас парой уточняющих слов у владельца (для этого есть «Вход в задачу» в `HOME.md`). Здесь — то, что требует исследования, времени или внешнего события.

## Правило

Критерий ответа фиксируется **до** начала поиска, не после. Иначе легко принять слабый ответ задним числом, подогнанный под то, что хотелось найти.

Куда искать ответ — не дублируется здесь, см. классификацию потребности в `ROUTING.md`.

## Статус

Как и в `DECISIONS.md`: запись не удаляется, только переклассифицируется. Закрытый вопрос остаётся в файле со статусом «закрыт» и ссылкой, где теперь живёт ответ (`MEMORY.md` / `knowledge/*`). Вопрос может быть явно переоткрыт — с датой и причиной, если закрытие оказалось ошибочным.

## Формат записи

```
### {дата} — {вопрос коротко}

Статус: Открыт / Закрыт / Переоткрыт
Вопрос:
Что считать ответом (зафиксировано до поиска):
Ответ (если закрыт):
Где теперь живёт ответ:
```

## Журнал

### 2026-08-12 — Как реально устроено прямое взаимодействие orchestrator→specialist агентов (вызов/результат/уточнение)

Статус: Закрыт
Вопрос: В системах, которые реально работают (не гипотетических), как технически устроен паттерн orchestrator/main-agent → specialist/research-agent → проверка результата → уточнение → повторный вызов: (1) какие проверяемые системы это реализуют, (2) формат передачи задачи, (3) формат возврата результата, (4) как orchestrator решает, что ответ достаточен, (5) как выглядит повторный вызов именно с уточнением, а не с нуля.
Что считать ответом (зафиксировано до поиска): минимум 2 реально проверенные системы, у каждой — разобранный механизм, не только упоминание существования; явно указано, что из найденного применимо к связке Engineer/ENGINEER-репозиторий ↔ Researcher/AI Intelligence-репозиторий, а что нет, и почему.
Ответ (если закрыт): нашлось 4 системы с разобранным механизмом, не одна конвергентная модель, а две структурно разные семьи. (а) Call-and-return, где specialist обязан отчитаться обратно ожидающему orchestrator: Claude Code subagents (контракт входа — только строка prompt, без истории; контракт выхода — финальное сообщение subagent verbatim; официально задокументированный механизм `resume` — `SendMessage` с ID агента, subagent получает назад полную историю и продолжает "exactly where it stopped", не с нуля) + LangGraph supervisor (`Command` совмещает обновление state и передачу управления; `create_handoff_back_messages` явно возвращает контроль supervisor'у; `interrupt()`/`Command(resume=...)` возобновляет ровно в точке прерывания). (б) Baton-pass/handoff, где управление передаётся без возврата по умолчанию: OpenAI Agents SDK — в официальной документации нет описанного канала возврата результата исходному агенту, это подтверждённый негативный факт, а не пробел поиска. Отдельная, самим Anthropic задокументированная практика (multi-agent research system, официальный блог-пост): lead agent оценивает достаточность результата **неявным LLM-суждением**, без формальной рубрики, и при недостатке — **порождает новый subagent, а не переоткрывает старый**; это прямо противоречит выводу об удобстве "resume" у Claude Code и уже описанному в `CAPABILITY_MAP.md` (Capability 5) правилу dsifry/metaswarm про обязательно свежего reviewer'а — три разных, осознанных ответа на один вопрос ("переиспользовать specialist или заменить"), не сведённые в одно правило. Полный разбор с источниками и confidence-тегами — в ответе этой сессии (Researcher, вызвана Engineer напрямую через недавно подтверждённый физический канал, 2026-08-12).
Где теперь живёт ответ: `knowledge/CAPABILITY_MAP.md` (раздел "Refinement — Orchestrator↔Specialist Invocation Contract"); `memory/2026-08-12.md`.

### 2026-08-12 — Реальные production-механизмы автоматического выбора Skills/tools-MCP/моделей и оптимизации стоимости («Capability System», 4 слоя)

Статус: Закрыт
Вопрос: как в реальных (не гипотетических) production AI-agent системах 2025-2026: (1) определяется, какие capabilities нужны задаче, (2) агент обнаруживает доступные Skills/tools/plugins, (3) выбирается конкретный инструмент среди доступных, (4) выбирается модель под подзадачу (не одна на всё), (5) оптимизируется стоимость/токены без потери качества — включая отдельно усиленный в ходе сессии вопрос про рост стоимости при параллельном fan-out нескольких фоновых агентов, (6) проверяется, что выбранный capability реально использован и дал результат, а не просто был вызван, (7) capabilities обновляются при появлении более современных вариантов — включая отдельно усиленный вопрос про периодическую (не разовую) переоценку/списание уже установленных capabilities, отличая «современный и подобранный под профессию набор» от «максимально много всего установлено», (8) какие из этих механизмов работают полностью автоматически, без человека в цикле. Второй прямой вопрос от Engineer в этот же день (после Batch ORCH), два уточнения получены и обработаны в ходе той же сессии (fan-out cost — реальный триггер из собственной сессии Engineer; периодическая переоценка capabilities — явное разделение «современно и упаковано» vs «максимум установлено»).
Что считать ответом (зафиксировано до поиска, критерий Engineer): минимум 2-3 реально существующие production-системы/паттерна, каждая разобрана на уровне механизма; по каждому из 8 под-вопросов — конкретный механизм + trade-off + источник, где нашлось; честное «не найдено» там, где не нашлось, не засчитанное как подтверждённое по умолчанию; отдельно — реальные противоречия между источниками, не сглаженные.
Ответ: нашлось 3+ независимых production-механизма выбора capabilities/моделей, разобранных на уровне устройства, не только названных — Anthropic tool search tool (BM25/regex поиск + `defer_loading`, официальная документация, >85% сокращение токенов, явный порог деградации точности выбора инструмента после ~30-50 доступных инструментов), RouteLLM/vLLM Semantic Router (калиброванный порог/BERT-классификатор по complexity, 85% экономии при 95% сохранённого качества), GPT-5 router (единственный найденный по-настоящему автоматический, обучаемый выбор модели под конкретное сообщение — но только внутри одного вендора, не между Claude/Gemini/Codex). По каждому из 8 пунктов — конкретный механизм и источник; два пункта дали честное «не найдено»: (4) автоматический межвендорный роутинг модели под подзадачу в проде не найден нигде — везде это ручной, статически спроектированный человеком пайплайн (например, «Claude пишет, Codex ревьюит»); (7, после усиления) периодическая (по расписанию) переоценка/списание уже установленных capabilities не найдена нигде, включая ближайший аналог из смежной инженерии (Dependabot/Renovate) — найден только вручную/по симптому вызываемый механизм (`mcp-audit`, `deadskills`, `skillreaper` — реальные, работающие инструменты с классификацией KEEP/DISABLE/REVIEW или active/zombie/dead, обязательным подтверждением человека, у части — обратимым карантином). По усиленному пункту 5 (рост стоимости при fan-out) — нашёлся прямой, количественно измеренный ответ: ролевое разделение по стоимости (дорогой оркестратор/дешёвые исполнители, официальная рекомендация Anthropic + независимый бенчмарк Arize: 96% качества при 46% стоимости) плюс честно названный контр-факт — независимый бенчмарк (Systima, «The Subagent Tax») показал, что параллельный fan-out в Claude Code стоил 2.6-5.9x токенов и не оказался быстрее ни на одной измеренной задаче. Зафиксировано прямое, не сглаженное противоречие: практика авто-обновления Skills без ревью человека (`npx skills update` из `main` при каждом старте сессии) существует рядом с прямо противоположной рекомендацией «после обновления модели вручную перепроверяй все skills», и ни один источник не примиряет эти два правила. Отдельно зафиксирован честный пробел процесса: заявленный координатором Skill `youtube-analysis` не найден в реальном списке доступных скиллов этой сессии — не вызывался, использован WebSearch/WebFetch по YouTube как замена, по собственному правилу `METHODOLOGY.md` про видео-источники.
Где теперь живёт ответ: `knowledge/CAPABILITY_MAP.md` (раздел "Refinement — Automatic Capability/Model Selection: Skills, Tools/MCP, Models, Cost"); сырое evidence — `knowledge/evidence/2026-08-12-capability-model-routing-selection.md`; реестр источников — `knowledge/EVIDENCE_INDEX.md`, Batch ROUTE; `memory/2026-08-12.md`.
