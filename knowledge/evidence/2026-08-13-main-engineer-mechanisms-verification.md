## Mechanism 1 — Symmetric cross-agent calibration + Tier-based write-asymmetry via "External Review Package"

**What the primary artifact actually says** (confirmed by direct fetch, not reconstructed from memory): `MAIN_ENGINEER_CORE.md` section 1.1 states the default — *"По умолчанию MAIN_ASSISTANT не пишет в `MAIN_ENGINEER/` и `AI_Projects/`; ты не пишешь в `MAIN_ASSISTANT/`"* — and a three-tier exception model: Tier 1 (UX/onboarding/mechanical/documentation changes, single authorization, direct write, logged to `MAIN_ASSISTANT/PENDING_REVIEW.md` for next-session review), Tier 2 (identity/architecture changes — Role Boundary, Brand Voice Filter, cognitive states/modes, memory architecture — require a formal External Review Package before integration), Tier 3 (cross-CORE changes affecting both agents symmetrically, including the write-asymmetry rule itself). `AGENT_PROTOCOL.md` confirms the same passport/tier discipline from the other agent's side but adds nothing new about the calibration mechanism itself. The `ENGINEERING_LOG/external_review_*` files show the mechanism actually exercised twice (v1.7.3, v1.7.4): MAIN_ENGINEER drafts a package from real session evidence, MAIN_ASSISTANT self-integrates ("write-асимметрия, я не редактирую его CORE напрямую") rather than being edited directly, and returns a structured self-audit before the package is closed. Default-to-Tier-2-when-uncertain is stated explicitly. **No external authority is cited for this mechanism in any of the four files** — it is presented purely as Maria's own operating contract between the two agents.

**External verification attempted**: searched for (a) production/framework multi-agent systems with tiered, risk-scaled write permission between agents, and (b) self-amending "agent constitution" patterns where one agent proposes a rule and a second agent integrates/audits it, rather than being edited by the first.

- **Partial structural analogs found, none matching the full pattern**:
  - Tiered/risk-scaled write permission between agents is real and documented in enterprise multi-agent governance write-ups (Arthur.ai; Architecture & Governance Magazine) and in a 2026 arXiv framework paper ("Beyond Autonomy: A Dynamic Tiered AgentRunner Framework," arxiv.org/pdf/2605.10223) which describes a "no write up" rule enforced by a router checking bearer-token scope per message — i.e. tiering exists in real multi-agent security architecture, but as a *centrally enforced routing policy*, not as a bilateral contract negotiated between two symmetric, independently-owned long-lived agents.
  - Self-amending "constitution" patterns exist and are structurally close on one axis: `github.com/Gamferno/agent-constitution` — a self-governing agent whose constitution is amended via GitHub PRs, reviewed by a dedicated `ReviewerAgent`/`ConstitutionAgent`/`AuditorAgent` before merge. This is the closest found analog to "a proposed change is not simply written in place, it passes through a structured review/audit step" — but it is one agent amending *its own* rules under multi-role internal review, not two independently-deployed peer agents where one proposes and the *other* self-integrates and reports back.
  - Anthropic's own Constitutional AI (2022) is the well-known origin of "constitution" language in this space, but it is a model-training technique (RLAIF against a written constitution), not a governance protocol between two deployed, long-lived agent instances — cited here only to rule it out as a match, not as supporting evidence.
  - MetaGPT and CAMEL (checked directly — MetaGPT's SOP-based role hierarchy paper/IBM writeup, CAMEL/Langroid comparison) give each agent role its own system prompt and message-pool subscription, but neither describes, nor was any evidence found describing, one agent role modifying another role's prompt or configuration under any tiering scheme.
- **Verdict: not found as a matching production/framework practice.** The specific combination this mechanism actually requires — two symmetric, independently-owned, long-lived agents; a proposer that gathers evidence from a real session and drafts a rule but does not edit the target directly; a target that self-integrates and returns a self-audit; and a three-tier classification keyed to the *class* of change (presentation vs. identity vs. both) rather than to system-level trust boundaries — was not located in any framework, paper, or production write-up reached this session. The closest partial matches (tiered RBAC-style enforcement; self-amending constitutions with internal reviewer roles) each share one axis of the pattern and diverge on the others, named explicitly above rather than smoothed into "yes, this exists." This is a genuine `[не найдено]` on the specific mechanism, not a confirmation with caveats.

## Mechanism 2 — "Business/usage Loop > Engineering Loop"

**What the primary artifact actually says**: `MAIN_ENGINEER_CORE.md` section 13.4, quoted directly — *"KPI MAIN_ENGINEER — не качество архитектуры. KPI — движение бизнес-метрик Марии. Правило: если архитектура улучшается, а бизнес-результат не двигается — архитектурные работы останавливаются."* A companion rule names the failure signal ("несколько итераций улучшения CORE/агентов без нового рабочего цикла") and the corrective sequence (stop architecture → diagnose what blocks the Working Loop → fix the blocker → only then resume improvements). `AGENT_PROTOCOL.md` states a related but distinct, narrower rule ("Working Loop First — если нельзя проверить сегодня, упрощай") that is about same-day verifiability, not about a usage-metric gate on architecture work. **No external authority is cited for either rule.**

**External verification attempted**: searched specifically for AI-agent companies/teams operating production agents that document this exact gate (architecture work halts when a usage/business metric doesn't move), as distinct from generic startup/product advice applied to AI without checking whether the same logic actually holds there.

- **The general shape is real, well-documented, and old** — but as generic startup/lean-product doctrine, not as an AI-agent-specific practice. Found and corroborated: Lean Startup's Build-Measure-Learn loop (the direct ancestor of "don't invest further in the product until the loop tells you to"); a16z's retention-first framing (`a16z.com/ai-retention-benchmarks`) and Sequoia's "Retention is... by far the best lever for product growth" (`articles.sequoiacap.com/retention`) both argue, for AI products specifically, that scaling/engineering investment should wait on retention/usage signal — this is the nearest real match found, and it does apply to AI products, but it is a scaling/PMF-readiness gate ("don't scale acquisition until retention holds"), not the same claim as "stop *architecture* work specifically, resume only once the blocker is fixed."
- **No source found** documenting, at the mechanism level (not just as a slogan), a real AI-agent-operating company or team that names this exact gate — "if the architecture improves but the usage/business metric doesn't move, architecture work stops until the real blocker is found and removed" — as a distinct AI-agent engineering practice.
- **Verdict: confirms the brief's own suspicion.** This reads as a real and reasonable generic startup/product-management principle (Lean Startup lineage, reinforced by a16z/Sequoia's retention-first framing applied to AI products) that was written into MAIN_ENGINEER_CORE.md as if it were an AI-agent-engineering-specific rule, without independent verification that AI agent engineering specifically needs or already uses this framing — exactly the risk named in the brief ("не общий generic startup/MVP совет, применённый к AI без проверки"). Not found: a company or team operating production AI agents that documents this as their own named practice. Reported as `[не найдено]` for the AI-agent-specific claim; the generic startup/PMF ancestor is real and cited above so the two are not conflated.

## Mechanism 3 — File passport header + ~300-line split threshold + Major.Minor.Patch versioning for agent-read instruction files

**What the primary artifact actually says**: this mechanism lives in `OBSIDIAN_PROTOCOL.md`, not in `MAIN_ENGINEER_CORE.md` as the brief's framing might suggest — confirmed by direct fetch. Exact quotes: *"Каждый `.md` файл обязан начинаться с паспорта"* (mandatory header: Версия/Дата/Тип/Статус/Связанные файлы — wikilinks); *"Признак нарушения: файл становится длиннее 300 строк — пора делить"*; and a Major.Minor.Patch scheme (Major = architecture changes, Minor = local improvements, Patch = bug fixes, with `1.0 → 2.0` and `1.0 → 1.1` given as examples). `AGENT_PROTOCOL.md` has its own, materially different length rule for its own file class — *"Документ длиннее 50 строк → /caveman сжатие"* — showing the old repo did not apply one uniform threshold even to itself; the 300-line number is `OBSIDIAN_PROTOCOL.md`'s own, not a cross-repo constant. **No external authority is cited for the passport, the threshold, or the versioning scheme in either file.**

**External verification attempted, three separate sub-claims** (this is the one mechanism of the three where solid, primary-source confirmation exists — reported precisely, not rounded up):

- **Length threshold triggers a mandatory split, specifically for a file an AI agent reads and acts on**: **confirmed**, and by the strongest possible source for this project — Anthropic's own official, current Skill-authoring guidance (`platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices`, fetched directly and read in full this session, hierarchy level 1). Verbatim: *"Keep SKILL.md body under 500 lines for optimal performance. Split content into separate files when approaching this limit"* — restated in the page's own checklist ("SKILL.md body is under 500 lines"). This is a real, current, official practice for exactly the class of file the mechanism is about (a file a live AI agent reads and acts on, not a human-facing doc). **One precise discrepancy, not glossed over**: Anthropic's own number is **500 lines**, not the ~300 old MAIN_ENGINEER's `OBSIDIAN_PROTOCOL.md` uses — the two are close in spirit (a numeric line ceiling that forces a split) but do not match in the specific number, and the ~300 figure that surfaced in one secondary WebSearch snippet (a third-party blog paraphrase) is not the number the primary Anthropic document itself states. Old MAIN_ENGINEER does not cite Anthropic for this rule, so this is not a misattribution case — it is independently arrived-at and happens to be in the same neighborhood, not sourced from the same place.
- **Major.Minor.Patch versioning specifically for agent-read prompt/instruction/config files**: **confirmed as real, current, documented industry practice**, converging across multiple independent sources this session (WebSearch-aggregated, not individually fetched in full — Medium confidence per this project's own tiering): Arthur.ai's prompt-versioning guide, Latitude.so, Agenta, aiquinta ("Versioning Agent Skills: SemVer, Compatibility, Deprecation"), tianpan.co. The convergent definition matches old MAIN_ENGINEER's scheme closely: Major = breaking/persona/structural change, Minor = added capability without behavior change, Patch = wording/typo fix with no material behavior change. This is a real, non-trivial match — not a generic software-versioning platitude, since these sources specifically address *prompt and agent-configuration* versioning, the same object class as the old repo's rule.
- **A mandatory structured header/"passport" (version/date/type/status/related-files) as an in-file frontmatter block, specifically for agent-read files**: **not confirmed** by any primary source reached this session. Anthropic's own Skill frontmatter spec requires exactly two fields (`name`, `description`) and nothing else — no version, date, status, or related-files fields anywhere in the spec. The closest real analog found is looser and lives one layer up, outside the file itself: prompt-versioning platforms (Arthur.ai) recommend attaching version metadata (author, timestamp, rationale, eval results) to each version in a *management layer*, not as a header block inside the file the agent reads. The specific "passport in the file itself" design is not found confirmed or denied by a primary source either way — reported as a genuine gap, not rounded up to "close enough" to the metadata-layer practice above.

**Overall verdict for Mechanism 3**: two of the three components are real, current, and independently confirmed by strong sources (Anthropic's own docs for the line-threshold-triggers-split principle; multiple independent vendor sources for prompt-file SemVer); the third (in-file structured passport header) has no confirming or disconfirming primary source and is reported honestly as unverified rather than assumed. No misattribution was found here specifically — old MAIN_ENGINEER does not claim any of this came from Anthropic or any other named authority, so the strong match to Anthropic's real practice is a genuine, independently-arrived-at convergence, not a citation being checked and found accurate.
