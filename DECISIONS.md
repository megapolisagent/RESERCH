# История и статус решений

> Не журнал. Действующий механизм: `HOME.md` и `UPDATE.md` обязаны сверяться с этим файлом в определённых сценариях, а не просто могут его почитать при желании.

## Как решение становится фактом

```
Proposal → Discussion → Locked
```

Переход между статусами разрешён только по явному подтверждающему слову владельца («принимаем», «фиксируем», «зафиксируй», «LOCKED») — никогда не выводится из тона реплики и никогда из того, что идею предложил сам владелец.

## Правила

- **Отклонённые альтернативы не удаляются.** Остаются в записи со статусом «отклонено» и причиной — защита от повторного предложения того же самого без нового аргумента.
- **После Locked — заморозка.** Обсуждение отклонённых вариантов прекращается немедленно. Снять заморозку может только явная команда владельца или прямой провал уже принятого решения на практике.
- **Решение не пересматривается без нового факта.** Следующий шаг конкретизирует и исполняет уже принятое, а не переоткрывает его заново. Работа, которая переживёт текущий диалог или затронет файлы устава — сначала короткая формулировка цели и границ, потом правки.
- **Высокий радиус поражения — пропорциональная проверка.** Решения, меняющие методологию работы агента, требуют проверки до Locked, но глубина проверки должна соответствовать масштабу и риску изменения. Для небольшого, чётко ограниченного изменения достаточно проверки владельцем и проверки на реальной задаче. Для изменений, затрагивающих фундаментальную архитектуру, роли, governance или большое число агентов, требуется независимая проверка отдельным изолированным ходом рассуждений. (Изменено 2026-08-13 — см. `Foundation/04_REPOSITORY/DECISIONS.md` того же дня, источник правки.)

## Кто и когда обращается к этому файлу

- **Перед новым предложением** — агент проверяет, не Locked ли это уже и не отклонялось ли раньше с обоснованием.
- **Перед правкой агентом собственных файлов устава** (`HOME.md`, `SOUL.md`, `ROUTING.md`) — обязательное чтение, см. `UPDATE.md`.
- **По прямому вопросу владельца** — «что мы решили по X».
- Рядовые задачи, не прошедшие входной фильтр по значимости, записи здесь не создают и сверяться с файлом не обязаны.
- Не читается при каждом старте сессии — как и дневник в `memory/`, это не часть капнутого уровня-1.

## Формат записи

```
### {дата} — {короткое название решения}

Статус: Proposal / Discussion / Locked / Отклонено
Что решается:
Обоснование:
Отклонённые альтернативы:
Источник:
```

### 2026-08-11 — Предложение: добавить поле «Последствия» в формат записи

Статус: Proposal
Что решается: добавить в формат записи (сейчас: Статус / Что решается / Обоснование / Отклонённые альтернативы / Источник) отдельное поле «Последствия» — что именно принято решением как цена/компромисс, а не только почему решение принято.
Обоснование: рыночное исследование (`research/AI-Engineering/`) независимо подтвердило ADR-дисциплину (Context + Decision + Consequences) как единственный формат документации решений, оказавшийся несущим, а не декоративным, у нескольких независимых проектов. Текущий формат уже close — «Обоснование» покрывает контекст, «Отклонённые альтернативы» уже сильнее многих реализаций ADR — но явного поля «что мы теряем этим выбором» нет.
Отклонённые альтернативы: не рассматривались — это первое предложение по этому вопросу.
Источник: `research/AI-Engineering/03-full-report.md` §1 (Integration), карточка «ADR discipline».
Примечание: это изменение самой методологии работы агента (формат `DECISIONS.md`) — по правилу этого же файла («высокий радиус поражения — независимая проверка перед Locked») не переводится в Locked этим же ходом рассуждений, который его предложил. Остаётся Proposal до отдельного рассмотрения.

### 2026-08-12 — Отношение этого файла к инлайн-решениям `skills/reverse-engineering/REVIEW_LOOP.md`

Статус: Proposal
Что решается: `REVIEW_LOOP.md` уже содержит собственную, обоснованную конвенцию — методологические решения о самом Skill логируются инлайн в изменённом документе (`PRINCIPLES.md`/`METHODOLOGY.md`/`REVIEW_LOOP.md`), не в отдельном decision-log файле, с явной причиной («держать один факт в двух файлах — та же ошибка, которую этот Skill сам находит у других»). Этот файл (`DECISIONS.md`) — Foundation-механизм, ожидаемый у любого агента. Вопрос: должны ли решения о методологии `reverse-engineering` переехать сюда, остаться инлайн, или это два разных класса решений (о методологии профессии vs о работе агента как системы), которым не нужно сходиться в один файл?
Обоснование: Engineering-ревизия (приведение Researcher к общей системе, 2026-08-12) сознательно не решает этот вопрос сама — он на границе структуры (Engineering, в полномочиях этой ревизии) и методологии Craft (не в полномочиях). Существующая конвенция `REVIEW_LOOP.md` не тронута и не мигрирована.
Отклонённые альтернативы: перенести существующие инлайн-решения `REVIEW_LOOP.md` в этот файл при заведении Foundation-структуры — отклонено явно владельцем при утверждении Engineering-плана: «не навязывай Researcher перенос существующих методологических решений».
Источник: `skills/reverse-engineering/REVIEW_LOOP.md`; решение владельца при утверждении Engineering-плана ревизии Researcher, 2026-08-12.
