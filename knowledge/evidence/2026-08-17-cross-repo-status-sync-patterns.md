## Pattern 1 — Git submodule: pointer to an exact commit, not a copy

**Source**: general git mechanism (`git-scm.com` submodule docs); corroborated by `opensource.com`, "Managing Git projects with submodules and subtrees"; `martinuke0.github.io`, "Mastering Git Submodules: A Comprehensive Guide for Developers" (2026-04-01) — both fetched via WebSearch aggregation this session, not individually full-fetched (Confidence: Medium — well-established, widely-documented git primitive, not a single fragile source).

**Mechanism**: a submodule entry in the parent repo is a gitlink — a reference to one specific commit SHA in another repository — not a copy of that repo's files. It does not auto-update; the parent repo's pointer only changes when someone explicitly runs `git submodule update --remote` and commits the new SHA. Because the pointer *is* the exact reference (not a separate description of it in prose), there is no state where the parent repo can claim a status that isn't literally what the pinned commit contains — the two can only ever be explicitly out-of-date (visible via `git status`/`git diff` on the gitlink) or in sync, never silently contradictory the way two independently-typed prose status words can be.

**Applicability verdict: adapt.** Literally submoduling one repo's `DECISIONS.md` file/repo into the other is heavier structural coupling than two independently-owned peer repos (Engineer/ENGINEER, Researcher/AI Intelligence) plausibly want — it would make one repo a technical dependency of the other in git's own dependency graph, not just a cross-reference. But the underlying mechanism — record a pointer to a specific, externally-verifiable commit rather than a restated status word — is adoptable without the submodule machinery itself: e.g. a status reference recording "as of commit `<sha>` in `<repo>`, status = X" is checkable (anyone can `git show <sha>:path` and see the literal text) in a way "Locked" as free prose typed independently in two files is not.

## Pattern 2 — ADR "superseded by" bidirectional link + Richards & Ford's centralization-not-duplication rule

**Source**: Michael Nygard's original Architecture Decision Record pattern (status field: proposed/accepted/deprecated/superseded — well-documented public standard, already logged as Medium confidence in this project's own `EVIDENCE_INDEX.md`, Batch SELF); Richards & Ford, *Fundamentals of Software Architecture*, quoted via `synchronium.github.io/software-architecture-wiki/concepts/adrs.html` (fetched directly this session): *"Richards & Ford recommend a wiki or shared directory (not a per-application Git repo, because cross-application and enterprise-level ADRs need to be accessible without repository access)"* — Application → Integration → Enterprise scoping hierarchy, with cross-cutting decisions living in exactly one centrally-accessible place rather than copied per-repo.

**Mechanism, two distinct parts**:
- (a) On supersession, both the old record (marked "Superseded by [new]") and the new record (marked "Supersedes [old]") explicitly link to each other — convention-based, not automated, but makes an out-of-date record self-flagging to anyone who opens it.
- (b) Decisions that cross repo/team boundaries are recommended to not be independently recorded per-repo at all — they belong in one shared location every affected repo reads, which prevents the "two independent copies drift" failure mode structurally rather than detecting it after the fact.

**Applicability verdict: (a) use as-is; (b) adapt.** (a) is a cheap, already-partially-converged-on convention — this project's own `OPEN_QUESTIONS.md` already does something adjacent (status changed by reclassification with a date/reason, not silent deletion) — and costs nothing to apply consistently to `DECISIONS.md` entries that get superseded. It does not by itself solve cross-repo drift, only makes any single repo's own record honest about its own history. (b) is the more directly relevant fix to the actual failure mode in the brief (same question, two different recorded statuses) — but Richards & Ford's literal fix (a wiki both sides read) assumes a shared access surface neither of these two independent git repos currently has. The transferable idea, not the literal wiki: a cross-cutting decision should have exactly one canonical recorded location; the non-owning repo should reference/point to it rather than maintain its own independently-typed copy of the status word.

## Pattern 3 — shields.io dynamic endpoint badge: live pull at render time, no stored copy

**Source**: shields.io official docs (`shields.io/docs/`), fetched via WebSearch aggregation (Confidence: Medium — official documentation, not individually full-page-fetched this session, but a well-known, stable, widely-used public mechanism).

**Mechanism**: a markdown image reference in repo B points to a `shields.io/endpoint` URL, which itself fetches a small JSON file hosted in repo A (typically via `raw.githubusercontent.com`) and renders it as a badge — fresh, on every page load. Repo B never stores the status text at all; there is nothing in repo B's own file content to go stale, because what's displayed is computed at view time directly from repo A's current file.

**Applicability verdict: reject** (for this specific system, despite being the cleanest zero-CI/zero-backend live-pointer mechanism found). Reasoning: it requires (1) a new external dependency on a third-party public service neither repo currently needs, and more importantly (2) it only resolves the drift problem for a *human viewing rendered markdown in a browser* — the "live" value exists only inside a rendered image, invisible to anything reading the raw markdown text, which is exactly how Engineer and Researcher (agents parsing files, not humans viewing GitHub's rendered UI) actually consume each other's `DECISIONS.md`. For an agent-read, git-only system, this pattern solves a problem this system doesn't primarily have (human-facing display drift) while leaving the actual one (raw-text drift between two independently-authored files) unaddressed. The one transferable idea it shares with Pattern 1 — "compute/verify from the canonical source instead of writing a static independent copy" — is already captured there, so this pattern doesn't add new adaptable substance beyond Pattern 1.
