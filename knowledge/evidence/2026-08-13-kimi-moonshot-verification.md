## 1. Where Kimi (K2/K3) is actually stronger/cheaper, with verified numbers

**Pricing — triangulated against the official platform and one independent aggregator, not marketing copy**:

- Official (`platform.kimi.ai/docs/pricing`, fetched directly, primary/official — Stage 2 hierarchy level 1–2): **Kimi K3** — $3.00/MTok uncached input, $0.30/MTok cached input, $15.00/MTok output, 1M-token context. Confirmed independently by Moonshot's own forum announcement (`forum.moonshot.ai/t/kimi-k3-is-here-our-most-capable-model/480`, fetched directly, official — same figures, plus "90%+ cache hit rate in coding, so most input costs $0.30").
- OpenRouter's listing (`openrouter.ai/moonshotai/kimi-k3`, fetched directly, independent aggregator of real provider pricing — level 3) shows a lower blended rate ($2.80/$14.00), i.e. one specific proxy/provider undercutting Moonshot's own list price — both numbers are real, they describe different sellers of the same model, not a contradiction.
- **Kimi K2.6** (the "everyday" tier below K3): official $0.60–0.95 input / $2.50–4.00 output depending on source, 262,144-token context (search-aggregated across DeepInfra, OpenRouter, NxCode — level 3, not individually re-fetched from Moonshot's own page this session, so held at Established/Medium rather than Confirmed).

**Direct comparison against the specific claim in the brief ("cheaper than Gemini for >200K-token workloads")** — this is the one number that matters most, and it was checked with real figures on both sides, not accepted as asserted:

- Gemini's own long-context pricing tier (>200K input tokens; search-aggregated across apidog.com/devtk.ai/pricepertoken.com, level 3, Gemini 3.1 Pro): **$4.00/MTok input, $18.00/MTok output** above 200K tokens (vs. $2.00/$12.00 below 200K).
- Kimi K3, same official figures as above: **$3.00/MTok input (uncached), $15.00/MTok output** — genuinely cheaper than Gemini's own long-context tier at every point, and dramatically cheaper on cache-hit input ($0.30 vs. Gemini's $0.20 cached, roughly comparable there, but K3's *uncached* rate already undercuts Gemini's *uncached* long-context rate).
- **Verdict: the "cheaper than Gemini above 200K tokens" claim holds**, checked with real official/aggregator numbers on both sides — Confirmed for the specific >200K-token comparison, not just plausible-sounding.

**Benchmarks — independent aggregator, not vendor self-reporting**:

- Artificial Analysis (`artificialanalysis.ai/models/comparisons/kimi-k2-6-vs-gemini-2-5-pro`, fetched directly, independent third-party benchmark aggregator — level 3): Kimi K2.6 scores 45 vs. Gemini 2.5 Pro's 26 on the Artificial Analysis Intelligence Index (a 9-benchmark composite: GDPval-AA v2, 𝜏³-Banking, Terminal-Bench v2.1, SciCode, HLE, GPQA Diamond, CritPt, AA-Omniscience, AA-LCR); Kimi is also cheaper per token in this pairing ($0.70 vs. $1.34/MTok blended) and has much lower time-to-first-token (2.82s vs. 21.65s) — but Gemini generates faster once started (131 tok/s vs. 49 tok/s) and supports a larger context window in this specific pairing (1M vs. K2.6's 260K — K3, not K2.6, is the 1M-context Kimi tier).
- On coding specifically: search-aggregated SWE-Bench Pro figures (buildfastwithai.com and others, level 3, not independently re-fetched from the raw leaderboard this session — Established/Medium) put Kimi K2.6 at 58.6%, ahead of GPT-5.4 (57.7%), Claude Opus 4.6 (53.4%), Gemini 3.1 Pro (54.2%) — a genuinely rare result (an open-weight model leading closed frontier models on a hard agentic-coding benchmark), not "close to" or "competitive with," if the aggregator's methodology is trusted.
- **Where it is rare and looks strong**: agentic tool-use/search tasks — BrowseComp 83.2%, DeepSearchQA F1 92.5% (vendor-cited figures via search aggregation, not independently cross-checked against a neutral leaderboard this session — held at Unverified-leaning-Established, not Confirmed, per Principle P4).

## 2. What tasks it is actually suited for

Converging signal across the independent (not vendor) benchmark sources above: **agentic coding** (SWE-Bench Pro, Terminal-Bench — a leading, not merely adequate, result per Artificial Analysis), **long-context knowledge work** (1M-token context at K3, cheaper than Gemini's own long-context tier at the same length), and **tool-using / search-heavy agentic tasks** (BrowseComp, DeepSearchQA — though these specific numbers are vendor-adjacent and less independently corroborated than the coding figures). No independent evidence was found this session of Kimi being the strongest choice for tasks outside these three clusters (e.g. no benchmark evidence gathered on creative writing, multilingual non-English-non-Chinese work, or multimodal image tasks specifically) — reported honestly as not investigated, not as ruled out.

## 3. What is actually known about Moonshot AI's data policy — checked independently, not accepted from AI_OS's own wording

This is the one point Engineer explicitly required be checked from scratch rather than trusted.

**What Moonshot's own privacy policy says** (`platform.kimi.ai/docs/agreement/userprivacy`, fetched directly, primary/official — level 1–2):
- Storage location, quoted directly: *"We store the information we collect in secure servers located in Singapore."*
- Training use: user content is used to "optimize our models... training and refining our underlying technology," with **no explicit opt-out** stated anywhere in the policy for this purpose.
- Data access: internal access is "strictly limited" to specific employees "when necessary"; external sharing extends to service providers, affiliates, and third parties in legal/corporate-transaction situations.
- Governing entity: the policy is issued by **MOONSHOT AI PTE. LTD.**, a Singapore entity, with supplementary terms for EEA/Switzerland/UK users under European data-protection law.
- Retention: "as long as necessary" to provide the service or meet legal obligations; account/input/payment data retained while the account is active.

**What is independently, separately known about the company itself** (checked because a Singapore-registered *policy entity* does not by itself prove where the underlying company/engineering org is based — this distinction is the actual substance of the jurisdiction question, and was not something the privacy policy alone settles):
- Wikipedia (`en.wikipedia.org/wiki/Moonshot_AI`) + South China Morning Post (`scmp.com/tech/big-tech/article/3273461/...`), both fetched via search, independent journalism — level 3, cross-corroborating: Moonshot AI is **headquartered in Beijing, China**, founded March 2023 by Yang Zhilin (Tsinghua University, ex-Carnegie Mellon/Meta/Google) and co-founders, with major funding from Alibaba, Tencent, Meituan, IDG Capital, and Chinese state-linked funds, valuation risen to ~$20B.
- **This is a real, verifiable, corroborated fact — the company itself is Chinese, Beijing-based, and Chinese-state-fund-backed** — independent of whatever the Singapore-entity privacy policy says about server location for the international API product.

**The specific "Beijing infrastructure / Chinese state legal access" claim, checked and found weak**:
- One secondary source (`aihackers.net/risks/kimi/`, fetched directly) asserts inference "routes through Moonshot's Beijing-based infrastructure" and that "the Chinese government has standing access rights under three distinct laws" — but on direct inspection, this source **cites no law, no registration record, no technical evidence for the infrastructure-location claim**, and its own companion verification page (`aihackers.net/verify/kimi-claims/`, fetched directly) explicitly lists "exact data center locations" among its own **unverified claims marked for follow-up**. This source is honest about its own gap but does not itself close it.
- No level 1–2 (primary/official) or level 3 (independent technical analysis) source was found this session that directly confirms or refutes whether the international API's Singapore-stated storage is the literal, only place inference/data actually reside, versus a legal wrapper around infrastructure genuinely reachable from Beijing.
- **Verdict, stated at the correct confidence tier**: **Confirmed** — Moonshot AI the company is Chinese, Beijing-headquartered, Chinese-state-fund-backed (independent journalism, cross-corroborated). **Established, single-source, and explicitly self-flagged-unverified** — the specific claim that inference is technically routed through Beijing infrastructure rather than genuinely Singapore-contained (the aihackers.net claim). **Confirmed, primary source** — Moonshot's own policy states Singapore storage and offers no training opt-out. AI_OS's original formulation ("не использовать для внутренних/конфиденциальных данных, юрисдикция — китайская компания") is **not fabricated** — the company-jurisdiction fact behind it is real and independently corroborated — but AI_OS presented it as if the infrastructure-routing mechanism were settled fact, when only the corporate-jurisdiction layer is actually confirmed at this session's evidence level; the technical-routing layer remains genuinely open, not quietly assumed closed in either direction.

## 4. Is there a real, current way to call Kimi from inside the Claude Code environment

Checked directly against Moonshot's own documentation, not inferred from the model name alone.

- **Official, primary-source-confirmed mechanism exists**: `platform.kimi.ai/docs/guide/claude-code-kimi`, fetched directly (official Moonshot docs, level 1–2) — Moonshot operates an Anthropic-API-compatible endpoint at `https://api.moonshot.ai/anthropic`. Setting `ANTHROPIC_BASE_URL` to that endpoint plus `ANTHROPIC_AUTH_TOKEN` (a Moonshot API key) and `ANTHROPIC_MODEL` (e.g. `kimi-k3`) in Claude Code's own configuration redirects the **entire CLI session** to Moonshot instead of Anthropic. This is real and documented by the vendor itself, not a community rumor — but it is a whole-session provider swap (it replaces Claude for the whole session, including whatever orchestrates it), not a per-subagent or per-task model choice sitting alongside Claude. The same official doc names a real limitation: WebFetch does not work through this endpoint ("the endpoint does not support WebFetch for now").
- **This is a different mechanism from the Agent tool's `model` parameter** that Engineer's own environment exposes (confirmed elsewhere as fact: only Sonnet/Opus/Haiku/Fable). The env-var redirect above operates one layer down, at the whole-CLI-session level, not through that parameter — it cannot be used to send *one* background subagent to Kimi while the rest of a session stays on Claude.
- **A separate, real but unofficial/third-party route exists for that narrower use case** (delegating one task to Kimi while the orchestrator stays on Claude): independent MCP servers — `kimi-api-mcp` (npm package, calls Moonshot's own OpenAI-compatible REST API `https://api.moonshot.ai/v1` directly, no CLI install, just a Moonshot API key) and `x51xxx/kimi-mcp-server` (GitHub, fetched directly — bridges Claude Code/Cursor/any MCP client to Moonshot's `kimi` CLI as a callable sub-agent tool; confirmed by direct README read to be an independent project by a named individual developer, explicitly not an official Anthropic or Moonshot integration, requiring separate `MOONSHOT_API_KEY`/Kimi Code CLI login). Neither is installed in this project's or Engineer's current environment (no `.mcp.json`/MCP entry for Kimi found in either repository this session) — this answers "does a way exist in the world," not "is it already available here."
- **Verdict**: technically, yes — a real way exists, **two distinct real ways**, not one: (a) an official, vendor-documented whole-session endpoint swap (`ANTHROPIC_BASE_URL` → `api.moonshot.ai/anthropic`), and (b) unofficial, third-party MCP bridges to Moonshot's own REST API for delegating a single task without replacing the whole session's model. Neither is "no way at all," and neither is a built-in Anthropic feature — both require deliberately reaching outside what Claude Code does by default.
