# FOUNDATION_ARCHITECTURE.md

Архитектурный план будущего Foundation Agent Home. Не содержимое документов — только их список, назначение и происхождение материала.

Источники — ровно три, без исключений:

- **Repository Library** (`00_SOURCE_LIBRARY/Dmitry_Repository_Library.md`) — 23 блока, извлечённых из репозитория Дмитрия (content-agent). Даёт рабочую реализацию, проверенную на живом курсе.
- **World Practices Library** (`00_SOURCE_LIBRARY/World_Practices_Library.md`) — отчёт по мировым практикам построения Agent Framework. Даёт принципы, независимо подтверждённые несколькими источниками рынка.
- **Foundation Construction Library** (`00_SOURCE_LIBRARY/Foundation_Construction_Library.md`) — 79 дословных блоков из 14 первоисточников (Anthropic, OpenAI, LangGraph, CrewAI, MCP, A2A, MemGPT, Letta, Generative Agents и др.), каждый с меткой Foundation Section. Даёт официальное подтверждение конкретной формулировкой первоисточника.

Если для какого-то файла материала в этих трёх библиотеках недостаточно или он есть только в одной из них — это указано прямо, без додумывания.

## instructions/

### HOME.md

**Назначение:** главный устав дома — кто агент, что читает при старте, стартовое меню, правила поведения. Аналог `CLAUDE.md` из репозитория Дмитрия, но без предметной специализации внутри.

**Источники:**

- **Repository Library** (Д-02 «Триада идентичности»): берётся структура файла — секции «Кто ты», «Что читать при старте», «Стартовое меню», «Правила», ссылка на реестр скиллов. Роль устава как отдельного, почти неизменяемого файла.
- **World Practices Library** (раздел 1 «Структура Agent Framework», раздел 11 «Лучшие практики»): берётся принцип «начинай с одного агента, эскалируй только когда нужно» и различение workflow/agent (Anthropic Building Effective Agents) как рамка для описания того, как агент решает, когда действовать по фиксированному сценарию, а когда — самостоятельно.
- **Foundation Construction Library** (Блок №001, №002, №008, №009 — Foundation Section: instructions; Блок №022–023 OpenAI Agents SDK primitives; Блок №010 12-Factor список факторов): берётся формулировка «маленький набор примитивов + простота по умолчанию» и явные принципы Anthropic («maintain simplicity», «prioritize transparency»).

**Почему именно так:** Repository Library показывает, как этот файл выглядит на практике у реально работающего агента (проверено на курсе). World Practices объясняет, почему эскалация сложности и разделение workflow/agent — это не прихоть одного автора, а сходящийся паттерн нескольких независимых команд. Construction Library подтверждает конкретной официальной формулировкой (Anthropic, OpenAI, 12-Factor), что «маленькое ядро + явные принципы простоты» — не общая фраза, а формулировка, которую разные источники используют дословно.

### AGENTS.md

**Назначение:** тонкая надстройка над `HOME.md` для рантаймов, которые ищут именно файл `AGENTS.md` (Codex и другие агенты, поддерживающие открытый стандарт).

**Источники:**

- **Repository Library** (Д-03 «Мультиагентное зеркало»): берётся сама идея тонкого адаптера — «устав один, AGENTS.md первым действием отсылает читать HOME.md целиком».
- **World Practices Library** (раздел 2 «Организация дома агента»): берётся статус AGENTS.md как открытого межвендорного стандарта под управлением Agentic AI Foundation / Linux Foundation, а не проприетарного решения одного инструмента.
- **Foundation Construction Library** (Блок №016–021 — весь раздел AGENTS.md, включая FAQ «Are there required fields?» и правило вложенности «closest file wins»): берётся точная формулировка стандарта — что это обычный markdown без обязательных полей, и правило приоритета при конфликте.

**Почему именно так:** Repository Library даёт архитектурный мотив (один источник истины + адаптер), но сам файл в репозитории Дмитрия написан для двух конкретных сред (Claude Code и Codex) и полон контентной специфики. World Practices показывает, что это не изобретение курса, а действующий открытый стандарт. Construction Library даёт точную формулировку правил стандарта напрямую с agents.md — этим текстом можно пользоваться почти без изменений, в отличие от версии из Repository, которую придётся депредметизировать.

### SOUL.md

**Назначение:** отдельный файл характера/тона агента, отделённый от устава и от профиля пользователя.

**Источники:**

- **Repository Library** (Д-02): берётся сама идея отдельного файла для тона — структура SOUL.md (характер + голос + запреты стиля) и обоснование, почему это не то же самое, что устав или профиль (разная частота изменения: устав почти неизменен, душа калибруется редко).
- **World Practices Library:** прямого независимого подтверждения этого конкретного файла в мировых практиках нет — вопрос тона агента в исследованных источниках обычно растворён внутри системного промпта, а не вынесен отдельным документом.
- **Foundation Construction Library:** отдельного блока под «файл характера» нет ни у одного из 14 источников.

**Почему именно так:** это единственный файл в текущем плане, обоснованный практически только одним источником (Repository Library) — честно отмечаю это как более слабое обоснование, чем у остальных файлов, а не скрываю. Решение включить его в план держится на структурном рассуждении Д-02 (три разные зоны ответственности с разной частотой изменения), а не на кросс-источниковом подтверждении. Это открытый вопрос для `04_DECISIONS`, а не установленный факт.

## profile/

### PROFILE.md

**Назначение:** анкета человека, для которого работает агент — кто он, в чём его контекст, что агенту нужно знать, чтобы не спрашивать одно и то же дважды. Изначально пустой шаблон.

**Источники:**

- **Repository Library** (Д-02, Ц-02 «Пустое состояние → бутстрап-интервью»): берётся структура `USER.md` (пустой шаблон с разделами) и, что важнее, механизм — правило «пустой профиль → не выдумывай, предложи интервью» + отдельный процесс сбора («распаковка»).
- **World Practices Library:** самостоятельного подтверждения именно «файла профиля человека» в мировых практиках нет — там речь в основном про память сессии/пользователя (session/user memory), а не про структурированную анкету.
- **Foundation Construction Library:** ни один из 79 блоков не имеет метки `profile` — раздел не подтверждён ни одним из 14 официальных источников напрямую.

**Почему именно так:** это второй открытый разрыв библиотеки. Файл включён в план, потому что механизм (Ц-02: детекция пустого состояния → бутстрап вместо галлюцинации) — сильная, самостоятельная архитектурная идея, но её конкретная файловая реализация (анкета `PROFILE.md`) подтверждена только Repository Library. Помечаю прямо: если этот пробел важен, стоит отдельно поискать источник именно на «профиль пользователя как файл», а не выводить его из вторичных соображений.

## memory/

### MEMORY.md

**Назначение:** единая система постоянной памяти агента верхнего уровня — то, что верно всегда и должно читаться при каждом старте.

**Источники:**

- **Repository Library** (П-01 «Трёхуровневая память»): берётся структура документа — лимит на объём (в примере 200 строк), разбивка на смысловые разделы, правило «читать всегда при старте».
- **World Practices Library** (раздел 3 «Память»): берутся архитектурные принципы — разделение потоковой/тредовой памяти и сквозной памяти как двух разных абстракций, подтверждённое у четырёх независимых крупных фреймворков (LangGraph Checkpointer/Store, OpenAI Sessions, LlamaIndex Context/Memory, Claude Agent SDK Sessions).
- **Foundation Construction Library** (Блок №052–054 LangGraph Checkpointer/Store, №026–029 OpenAI Sessions, №069–071 MemGPT main context/FIFO queue, №077–079 Generative Agents memory stream, №056–057 CrewAI Memory, №063 AG2 knowledge store): берутся правила организации памяти и её жизненного цикла из первых рук — конкретные механизмы разграничения короткой и долгой памяти, эвикции, ранжирования при чтении.

**Почему именно так:** Repository показывает рабочую реализацию — конкретный, проверенный на практике формат файла с лимитом строк. Мировые практики объясняют принцип (короткая vs долгая память — это не прихоть, а сходящийся паттерн). Construction Library подтверждает эти решения официальными источниками — это ровно тот пример, который вы сами привели как образец.

### memory/ (папка: дневник + правки)

**Назначение:** хроника по дням («что делали, где остановились») и отдельный поток правок от человека, который не даёт агенту повторять одну и ту же ошибку.

**Источники:**

- **Repository Library** (П-01, П-02 «Шаблон правки»): берётся структура `memory/ГГГГ-ММ-ДД.md` (три обязательных поля: что сделали / что осталось / решения) и отдельный шаблон `memory/feedback_<тема>.md` (Было → Правка → Правильно) с правилом «записывать без спроса».
- **World Practices Library** (раздел 3): берётся принцип эпизодической/хендофф-памяти (session summary, переносимый в следующую сессию) как общий паттерн.
- **Foundation Construction Library** (Блок №027 OpenAI Sessions «Before each run... After each run»; Блок №074 Letta «old information is evicted as new information is added»): берётся официальная формулировка правил цикла чтения/записи такой памяти.

**Почему именно так:** структура дневника и, отдельно, шаблон правки — это два разных, проверенных на практике механизма из Repository. Мировые практики подтверждают сам класс механизма (эпизодическая память), но не конкретный формат правки-фидбека — этот формат специфичен для Repository и не подтверждён напрямую двумя другими источниками; включаю его, потому что он не противоречит найденным принципам, а не потому, что найдено прямое подтверждение.

## knowledge/

### knowledge/ (папка: тематические копилки)

**Назначение:** растущая база знаний, которую агент копит по темам и читает точечно под конкретную задачу, а не загружает всю сразу.

**Источники:**

- **Repository Library** (П-03 «Самодокументирующиеся копилки», П-04 «Таблица роутинга»): берётся приём «схема живёт рядом с данными» (каждый файл сам объясняет формат своей записи) и правило точечного чтения по задаче.
- **World Practices Library** (раздел 4 «Знания», раздел 7 «Управление контекстом»): берётся принцип progressive disclosure (не грузить всё в контекст сразу) и находка про ADR, превращённые в машинно-проверяемые ограничения — как более развитая версия «копилки знаний».
- **Foundation Construction Library:** только один блок с меткой `knowledge` во всей библиотеке (Блок №043, MCP Resources — «application-driven» ресурсы, управляемые приложением, а не моделью).

**Почему именно так:** это третий и самый явный разрыв. Repository даёт рабочий, проверенный формат (шаблон в шапке файла + точечное чтение), мировые практики независимо подтверждают сам принцип progressive disclosure — но именно раздел `knowledge` в Construction Library почти пуст: 14 официальных источников, которые я открывал напрямую, в основном говорят про *память* (session/agent memory), а не про отдельно стоящую *базу знаний* в файлах. Это значит: секция `knowledge/` в плане опирается на Repository + общий принцип из World Practices, но не имеет прямого официального подтверждения конкретной файловой формы — стоит либо доследовать этот раздел отдельным проходом (ADR-инструменты, RAG-паттерны), либо явно принять это решение как собственное, а не заимствованное.

## routing/

### ROUTING.md

**Назначение:** таблица «сигнал задачи → что читать / что делать», плюс правило, когда агент показывает меню выбора, а когда сразу берётся за работу по прямой фразе.

**Источники:**

- **Repository Library** (П-04, Ц-03 «Меню + обход по триггер-фразам»): берётся сама таблица роутинга по knowledge/ и механизм «стартовое меню + список триггер-фраз мимо меню».
- **World Practices Library** (раздел 1 «Структура Agent Framework», подпункты про Handoff vs tool-call и эскалацию сложности): берутся принципы маршрутизации между несколькими путями выполнения.
- **Foundation Construction Library** (Блок №003–007 Anthropic — паттерны Prompt Chaining/Routing/Parallelization/Orchestrator-workers/Evaluator-optimizer; Блок №018–019 AGENTS.md — правило «ближайший файл побеждает»; Блок №031 Claude Agent SDK — автоматическая инвокация субагента по `description`; Блок №055 LangGraph — «не смешивай статичную и динамичную маршрутизацию в одном узле»): берутся официально сформулированные паттерны маршрутизации.

**Почему именно так:** Repository показывает пользовательский UX-слой роутинга (меню + фразы-триггеры для новичка). World Practices и Construction Library вместе дают инженерный слой — как формально устроена маршрутизация внутри системы (routing/handoff/orchestrator паттерны). Файл объединяет оба слоя: человеко-ориентированный вход и машинно-ориентированную маршрутизацию под капотом — но именно поэтому в `04_DECISIONS` стоит явно решить, не разделить ли их на два файла, если это станет громоздким.

## skills/

### skills/ (склад) и `.home/skills/` (установленные)

**Назначение:** разделение «что вообще может быть подключено» (склад) от «что реально подключено прямо сейчас» (рабочий стол), плюс единый формат самоописания способности.

**Источники:**

- **Repository Library** (Д-01 «Дом vs Склад», С-01 «Контракт SKILL.md», С-02 «Триггер через description», С-03 «references/ как локальная база»): берётся вся механика разделения склад/рабочий стол, формат фронтматтера SKILL.md, правило подгрузки references/ по требованию.
- **World Practices Library** (раздел 7 «Модульность и расширяемость», раздел 6 «Организация документации»): берётся принцип «registry + самоописывающийся манифест + разрешение при установке» как универсальная форма расширяемости, независимо подтверждённая в MCP Registry и Claude Code Plugins.
- **Foundation Construction Library** (Блок №041–044 MCP capability negotiation/tools/prompts; Блок №030, №033 Claude Agent SDK subagents/skills; Блок №058–059 CrewAI `create skill`; Блок №065 AG2 tools/toolkits; Блок №067 Semantic Kernel plugins): берётся официальная формулировка того, как разные платформы независимо друг от друга описывают модель подключаемой способности (кто её вызывает — модель или пользователь, как она регистрируется).

**Почему именно так:** это самый плотно подтверждённый раздел всей библиотеки — все три источника независимо сходятся на одной и той же форме (манифест + основное тело + опциональные референсы, вызов по естественноязычному описанию). Repository даёт полностью рабочую, проверенную на практике реализацию; World Practices показывает, что это не частное решение курса, а сходящийся отраслевой паттерн; Construction Library подтверждает это дословно у MCP, Claude Agent SDK, CrewAI, AG2 и Semantic Kernel одновременно.

### Скилл `installer` (мета-скилл)

**Назначение:** единственная задача — управлять составом остальных скиллов (поставить/обновить/зарегистрировать), а не решать предметную задачу.

**Источники:**

- **Repository Library** (У-01 «Установщик как мета-скилл», У-02 «Sparse checkout», У-03 «Карта имён + статусы», У-04 «Реестр установленных скиллов»): берётся вся механика — команда установки одной строкой, карта «человеческое имя → техническое имя папки», реестр факта установки.
- **World Practices Library** (раздел 8 «Обновление агентов», раздел 7 «Модульность»): берётся принцип «registry + manifest + install-time resolution» на уровне рынка (MCP Registry, Claude Code Plugin Marketplaces) как рамка, в которую укладывается механизм установщика.
- **Foundation Construction Library** (Блок №058–059 CrewAI CLI `create skill`; блоки MCP capability negotiation №041): берётся официальное подтверждение самой идеи CLI-скаффолдинга способности как отдельной команды.

**Почему именно так:** Repository — единственный источник, где этот мета-скилл реализован полностью и проверен вживую (включая зафиксированную историю отказа от более простой, но ломающейся схемы с `rm -rf`). Мировые практики и Construction Library подтверждают рамку (registry+manifest), но ни у одного из 14 официальных источников нет полного аналога именно диалогового установщика, вызываемого фразой «поставь скилл X» — это управленческая надстройка, специфичная для Repository, встроенная в общепринятую архитектуру расширяемости.

## update/

### UPDATE.md + update.sh

**Назначение:** правила и механизм безопасного обновления служебной части дома без риска затереть накопленные пользователем данные.

**Источники:**

- **Repository Library** (У-05 «Safe-update: служебное vs личное», У-06 «Два уровня обновления»): берётся вся механика — списки обновляемых/защищённых файлов, контрольная сумма личных файлов до/после с жёсткой остановкой при расхождении, два уровня (один скилл / весь служебный слой).
- **World Practices Library** (раздел 10 «Обновление агентов»): берутся принципы — неизменяемый версионированный артефакт + закреплённая версия на исполнение, правило «не меняй версию посреди уже идущего диалога», подтверждённое шестью независимыми источниками и одним реальным постмортемом.
- **Foundation Construction Library** (Блок №020–021 AGENTS.md «treat as living documentation» + governance; Блок №039–040 MCP Lifecycle Initialization/Operation/Shutdown; Блок №048 A2A TaskState; Блок №066 AG2 Current Focus Areas): берётся официальная формулировка того, как разные протоколы описывают собственный жизненный цикл и версионирование.

**Почему именно так:** Repository даёт единственную во всех трёх источниках *реализацию*, которая математически доказывает сохранность личных данных (контрольная сумма до/после), а не просто обещает её. World Practices показывает, что принцип «framework обновляем, state неприкосновенен» и «версия закрепляется на весь диалог» — это отраслевой консенсус, подтверждённый в том числе разбором реального инцидента. Construction Library подтверждает, что понятие жизненного цикла (init → operation → shutdown/deprecated) заложено в сами протоколы (MCP, A2A) на уровне спецификации, а не изобретено отдельно для курса.

## workspace/

### workspace/ (папка результатов)

**Назначение:** место, куда агент кладёт готовые результаты работы — с заранее заданной, но пустой структурой подпапок под типы результата.

**Источники:**

- **Repository Library** (Д-04 «Пустой каркас (.gitkeep-скелет)»): берётся сам приём — папки существуют пустыми с понятной номенклатурой подпапок, ничего не подделывается заранее.
- **World Practices Library:** прямого отдельного раздела про «папку результатов» в отчёте нет; ближайшее — общие замечания про структуру документации и контекст.
- **Foundation Construction Library** (Блок №024 OpenAI Agents SDK «Sandbox agents: Run specialists inside real isolated workspaces with manifest-defined files»; Блок №032 Claude Agent SDK — изоляция контекста субагента): берётся официальное подтверждение идеи изолированного рабочего пространства как самостоятельного архитектурного понятия (`workspace`), отдельного от памяти диалога.

**Почему именно так:** Repository даёт конкретный, минималистичный приём (пустые папки с понятными именами) — то, что реально стоит скопировать как структуру. Construction Library неожиданно подтверждает более развитую версию той же идеи на уровне двух современных SDK (OpenAI Sandbox agents, Claude Agent SDK) — там «рабочее пространство» уже осмыслено как отдельная, изолируемая, ресурсоёмкая сущность, а не просто папка. World Practices эту тему отдельно не поднимает — это единственный раздел, где Construction Library даёт больше, чем отчёт по рынку.

## communication/

### COMMUNICATION.md

**Назначение:** правила взаимодействия, когда в доме появляется больше одного агента (субагенты, параллельные инстансы, внешние агенты) — как они получают контекст друг от друга и как передают управление.

**Источники:**

- **Repository Library:** прямого материала нет. Контент-агент — одноагентная система; ближайший аналог (Д-03, мультиагентное зеркало Claude Code/Codex) — это не взаимодействие *агентов между собой*, а дублирование одного и того же устава для двух рантаймов. Честно фиксирую: раздел `communication` не имеет опоры в Repository Library вообще.
- **World Practices Library** (раздел 1, подпункт про Handoff vs tool-call; раздел 7, разграничение MCP/A2A): берётся ключевое разграничение — «агент↔инструмент» (MCP) и «агент↔агент» (A2A) как два разных уровня, которые легко перепутать, плюс общий паттерн handoff/agents-as-tools с явной семантикой «кто владеет финальным ответом».
- **Foundation Construction Library** (Блок №037–038, №041 MCP Architecture — Host/Client/Server; Блок №045–049 A2A — Introduction, Guiding Principles, Specification Structure, TaskState, Message): берётся официальная формулировка обоих протоколов практически целиком — это единственный раздел плана, который целиком выведен из двух источников (World Practices + Construction Library) без какой-либо опоры на Repository.

**Почему именно так:** это самый честный пример того, зачем нужны три источника, а не один. Repository ничего не может дать этому разделу — в нём просто нет многоагентной архитектуры. World Practices объясняет, зачем вообще разводить два протокола (агент-инструмент и агент-агент), а Construction Library подтверждает это дословными формулировками официальных спецификаций MCP и A2A. Файл включён в план исключительно на основании двух источников из трёх — и это нормально, но должно быть явно видно, а не смешано с разделами, где сходятся все три.
