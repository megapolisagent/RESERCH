# FOUNDATION_DECISIONS.md

Журнал решений по сборке репозитория. Одна запись на файл. Ничего не удаляется задним числом — если решение потом пересматривается, добавляется новая запись со ссылкой на старую, а не правится старая.

Критерий отбора, действующий начиная с MEMORY.md и далее для всех файлов:

> Без этого элемента Foundation перестанет выполнять свою роль как универсальная база для любого агента (Obsidian, Engineer, Research, Producer и т.д.)?
> Если ответ «нет, любой агент проживёт без этого поля» — элемент не фундаментальный, даже если он полезен для части агентов.

## MEMORY.md

**Источник (Blueprint):** Repository → П-01. World Practices → раздел 3 (Память), LangGraph/OpenAI Sessions/LlamaIndex/Claude Agent SDK. Construction Library → №052–054 (LangGraph Checkpointer/Store) как релевантные MEMORY.md напрямую; №026–029, №056–057, №063, №069–071, №077–079 при проверке оказались о механизме сессий/скоринга, а не о файле уровня-1 — отложены к `memory/` и будущему `instructions/memory-rules.md`.

### Клонировано без изменений
- Заголовок-комментарий: «Уровень 1 памяти», лимит 200 строк, правило «агент дописывает сам».
- Секция «Кто я» (структура и назначение поля).
- Секция «Ключевые решения» (структура и назначение).

**Почему без изменений:** это уже архитектура, не предметная реализация — правки не требовались ни одним источником.

### Изменено
- Секция «Кто я»: убрана привязка к брендированному названию процесса сбора данных («заполнится на распаковке») — оставлено нейтральное «заполняется при первом знакомстве с владельцем». В формулировку добавлено обоснование необходимости поля.

**Из какого источника:** обоснование поля («минимальная идентичность, необходимая для непрерывности поведения между сессиями») — собственный вывод в ходе проверки карты по критерию отбора, не взято дословно ни из одного источника; проверено и принято в диалоге, ссылки на конкретный блок не имеет.

**Почему это усиливает Foundation:** поле теперь обосновано независимо от того, будет ли в доме отдельный файл профиля пользователя — раньше обоснование («сжатый указатель на PROFILE.md») ломалось бы, если PROFILE.md не будет существовать или будет устроен иначе.

**Почему исходная реализация была недостаточна именно здесь:** у Дмитрия поле было обосновано только косвенно (через ссылку «подробно — в USER.md») и названо термином курса («распаковка»), не переносимым в предметно-нейтральный дом.

### Удалено (не перенесено в Foundation)
- Секция «Моя ниша и продукт» целиком, включая поле «Куда веду подписчика».
- Секция «Мои площадки» (Instagram/YouTube/Telegram) — без обобщённой замены.
- Секция «Цель на программу» (+1000 подписчиков).

**Из какого источника решение об удалении:** ни один из трёх источников не подтверждает поля «ниша», «продукт», «площадки», «числовая цель программы» как обязательные для MEMORY.md. Проверка по критерию: Engineer- и Research-агент не теряют функциональности при отсутствии любого из этих полей.

**Почему это усиливает Foundation:** предотвращает утечку предметной специализации в уровень-1 памяти, который должен быть одинаков для любого агента. Также соблюдено отдельное правило «не заменять удалённое обобщённой формулировкой» (Instagram → «Communication Channel» и подобное намеренно не сделано, чтобы не создавать выдуманную архитектуру, не подтверждённую источниками).

**Почему исходная реализация была недостаточна именно здесь:** эти секции у Дмитрия писались для одного типа агента (контент-продюсер) и предполагают наличие ниши/продукта/платформ/числовой цели как данность — что верно не для всех будущих специализаций Foundation.

### Дополнено с обоснованием источника
- Разделение MEMORY.md (уровень 1, долгая память) и `memory/` (дневник, короткая/тредовая память), уже существующее у Дмитрия, получило независимое подтверждение: LangGraph разделяет Checkpointer (short-term, thread-scoped) и Store (long-term, cross-thread) тем же способом (Construction Library, Блок №052–054). Текст файла не изменён — подтверждение зафиксировано здесь, а не встроено в сам файл.

**Почему это усиливает Foundation:** показывает, что двухуровневое разделение памяти — не произвольное решение одного автора, а паттерн, независимо воспроизведённый в промышленном фреймворке.

## PROFILE.md

**Источник (Blueprint):** Repository → Д-02, Ц-02. World Practices → нет. Construction Library → нет.

### Клонировано без изменений
- Правило пустого состояния: «не выдумывай факты о владельце, а сначала предлагай знакомство» (Ц-02).

### Изменено
- Заголовок: убрано слово «контент» из «чтобы делать контент под меня» → «для кого работает агент».

**Из какого источника:** депредметизация payload, ранее согласованная как действующая договорённость (Этап 1), не новое решение.

### Удалено (не перенесено в Foundation)
- «Моя экспертиза», «Мои темы», «Моя ниша и аудитория», «Мои площадки», «Формат съёмки», «Мой голос».

**Из какого источника решение об удалении:** ни один из трёх источников не подтверждает эти поля как обязательные. Проверка по критерию: Engineer/Research-агент не теряют функциональности без любого из них. «Мой голос» — самый спорный случай (интуитивно кажется более универсальным, чем «ниша»), но критерий применён без исключений.

**Почему это усиливает Foundation:** после строгой проверки от файла осталось только поле «Кто я» — то есть содержательно то же, что уже подтверждено в MEMORY.md.

**Почему исходная реализация была недостаточна именно здесь:** `USER.md` у Дмитрия проектировался для одной специализации (личный бренд контент-эксперта) и почти целиком состоит из полей, специфичных для неё.

### Важная находка (не решение, а зафиксированный факт для будущего пересмотра)
После удаления payload-полей `PROFILE.md` и «Кто я» в `MEMORY.md` содержательно почти совпадают. Отдельное существование файла обосновано не богатством содержания, а принципом progressive disclosure (World Practices, раздел 7; Construction Library, множество блоков): `MEMORY.md` — короткий, с лимитом, всегда загружается; `PROFILE.md` — без лимита, читается точечно, точка роста для будущих специализаций. Если это обоснование в будущем не подтвердится практикой (файл останется пустым и невостребованным даже у специализированных агентов) — кандидат на слияние с MEMORY.md, но не сейчас.

## HOME.md

**Источник (Blueprint):** Repository → Д-02. World Practices → раздел 1, раздел 11. Construction Library → №001, №002, №008, №009, №010, №022, №023.

### Клонировано без изменений
- «Что читать при старте» (порядок чтения файлов).
- «Первая встреча» — механизм (Ц-02).
- «Сбор контекста до первого действия».

### Изменено
- «Кто ты» — контентная роль заменена плейсхолдером `[РОЛЬ — заполняется специализацией]`, а не изобретённым обобщённым текстом.
- «Стартовое меню» — фиксированные пункты (💡 Идея и т.д.) удалены; оставлен хук «если специализация задаёт меню — покажи, если нет — работай по триггер-фразам».
- «Роутинг в knowledge/» и «Обновление агента» — не клонированы целиком, заменены ссылками на `ROUTING.md` и `UPDATE.md` (эти файлы отдельно по Blueprint).
- «Правила» — убран пункт про простой язык для новичка (специфика курса/аудитории, место в SOUL.md); в оставшихся пунктах убраны слова «продюсер», «контента», «ученика».
- «Память» — сжата до краткого якоря с ссылкой на `instructions/memory-rules.md`, вместо полного объяснения трёх уровней внутри HOME.md.

**Из какого источника:** депредметизация — действующая договорённость Этапа 1. Решение не дублировать роутинг/обновление внутри HOME.md — прямое следствие того, что Blueprint назначил эти темы отдельным файлам; дублирование создало бы два источника истины для одного и того же правила.

**Почему это усиливает Foundation:** HOME.md перестаёт быть монолитом на 145 строк, как у Дмитрия, и становится тонким уставом с явными точками подключения (специализация, ROUTING.md, UPDATE.md, SOUL.md) — при добавлении новой специализации не нужно трогать HOME.md вообще, только то, что она реально меняет.

**Почему исходная реализация была недостаточна именно здесь:** у Дмитрия устав и специализация (меню, роутинг, обновление) физически лежат в одном файле — это работает для одного продукта, но не масштабируется на несколько специализаций поверх одного Foundation без переписывания HOME.md под каждую.

### Удалено (не перенесено в Foundation)
- Конкретные пункты стартового меню (💡🎬✍️🎥🧲) и их триггер-фразы.
- Правило «простой язык для новичка, терминала боится».

**Из какого источника решение об удалении:** ни один из трёх источников не подтверждает конкретный набор режимов работы как обязательный для любого агента — это специализация по определению.

## AGENTS.md

**Источник (Blueprint):** Repository → Д-03. World Practices → раздел 2 (AGENTS.md как стандарт). Construction Library → №016–021.

### Клонировано без изменений
- Принцип «первым действием прочитай устав целиком, этот файл — только надстройка».

### Изменено
- Имя устава `CLAUDE.md` → `HOME.md`.
- «Кто ты» — плейсхолдер вместо контентной роли, той же логикой, что и HOME.md.

### Удалено (не перенесено в Foundation)
- Механика зеркалирования `.codex/skills` ↔ `.claude/skills`.
- Разделы «Память человека — не трогать» и «Правила, о которых чаще всего забывают» — дублировали HOME.md.

**Из какого источника решение об удалении:** зеркалирование двух конкретных рантаймов — реализационная деталь Д-03, отмеченная в Blueprint как «частично» универсальная; Foundation пока не привязан к конкретным рантаймам, поэтому переносить именно эту механику преждевременно — сохранён только принцип единого склада. Дублирование правил удалено на основании собственного принципа файла («устав один») — источник решения не внешний, а внутренняя логика самого документа, вскрытая при сборке.

**Почему это усиливает Foundation:** AGENTS.md теперь буквально тонкий — 6 строк содержательного текста против дублирующего блока у Дмитрия. Правки правил делаются один раз, в HOME.md, а не в двух местах, которые могут разойтись.

**Почему исходная реализация была недостаточна именно здесь:** у Дмитрия AGENTS.md декларирует «устав один», но не следует этому до конца — дублирует часть правил. Это несогласованность оригинала, а не архитектурное решение, которое стоило бы копировать.

## SOUL.md

**Источник (Blueprint):** Repository → Д-02 (единственный источник). World Practices → нет. Construction Library → нет.

### Клонировано без изменений
- Структура файла как отдельного слота для характера (сам факт, что характер — не в HOME.md и не в PROFILE.md).

### Удалено (не перенесено в Foundation)
- Все 6 черт характера («режешь воду прямо» и т.п.).
- Раздел «Голос контента» целиком.
- Раздел «Запреты стиля» — пункт «выдуманные цифры» удалён как дубль Ц-01 (уже в HOME.md), остальные пункты — как специфика бренда курса.

**Из какого источника решение об удалении:** ни World Practices, ни Construction Library не подтверждают ни один конкретный пункт характера или запрета стиля. Repository — единственный источник, и он описывает конкретный, не универсальный характер.

**Почему это усиливает Foundation:** файл больше не навязывает конкретный характер (тёплый наставник для новичка) всем будущим специализациям — Research-агент и Engineer-агент могут иметь совершенно разный, даже противоположный характер, и оба должны иметь одинаковое право задать его через один и тот же файл.

**Почему исходная реализация была недостаточна именно здесь:** у Дмитрия характер жёстко зашит в файл вместе со слотом для него — то есть SOUL.md одновременно и объявляет «здесь живёт характер», и уже содержит конкретный характер. Для Foundation это два разных вопроса, и второй не подтверждён ни одним источником, кроме одного.

### Примечание к находке
Третий файл подряд (после PROFILE.md), который после строгой проверки остаётся почти пустым слотом, а не содержательным документом. Вынесено отдельно в `FOUNDATION_OBSERVATIONS.md` (Наблюдение 1) — не влияет на уже собранные файлы.

## COMMUNICATION.md

**Источник (Blueprint):** Repository → нет. World Practices → раздел 1, раздел 7. Construction Library → №037–038, №041, №045–049.

### Важная находка перед сборкой
Строгая проверка по критерию необходимости показала: Foundation v1 — одноагентный дом, ни один из 12 уже собранных файлов не создаёт и не координирует несколько агентов. Файл не проходит тест «без этого элемента Foundation перестанет быть универсальной базой» в том смысле, в каком его проходит, например, HOME.md. Решение — не имитировать готовый механизм, а зафиксировать только то, что подтверждено: разграничение агент↔инструмент (уже покрыто `skills/`) и агент↔агент (не покрыто ничем).

- Весь файл — нет реализации Дмитрия, которую можно было бы взять за основу.

**Из какого источника:** различение двух протоколов — прямая формулировка World Practices (раздел 7) и Construction Library (№041: «MCP is for agent-to-tool... A2A is for agent-to-agent... complementary»). Ничего не изобретено сверх этого различения — конкретные правила (кто владеет ответом, как передаётся задача) сознательно не написаны, потому что ни один источник не даёт основания зафиксировать их именно сейчас, для дома, где такого механизма ещё не существует.

**Почему это усиливает Foundation:** файл не притворяется рабочим протоколом, которого нет — вместо этого явно маркирует место, куда протокол ляжет, и предупреждает не решать эту задачу обходным путём через `skills/` (что было бы реальным риском смешать два разных протокола в одном месте — ту же ошибку, от которой уже предостерегает `ROUTING.md`).

**Почему исходная реализация была недостаточна именно здесь:** у Дмитрия многоагентности нет вообще — не потому что решение плохое, а потому что задача не стояла. Перенести нечего.

**Почему исходная реализация была недостаточна именно здесь:** ни MCP/A2A, ни Repository, ни Construction Library в v1-сборке не давали разделения «потребность vs инструмент» — оно пришло только из архитектуры MAIN_ASSISTANT, независимо подтверждённой сторонним источником (Visual Engineering).

## Sources of Truth (расширение instructions/memory-rules.md)

**Источник (Blueprint):** Chief Design Officer (Sources of Truth hierarchy — «конфликт решается сейчас, в самой доктрине», единичный источник в археологии).

### Усилено (не новая сущность)

- Добавлен раздел «Когда источники расходятся» с порядком доверия `DECISIONS.md` (Locked) → `MEMORY.md` → более свежий дневник → `knowledge/`.

**Почему усиление, а не новый файл:** `instructions/memory-rules.md` уже владеет ответственностью «как устроена память» — правило конфликта источников относится к той же ответственности, не к новой.

**Почему это усиливает Foundation:** до этого момента ни один файл не отвечал на вопрос «что делать, если `MEMORY.md` и `knowledge/` говорят разное» — расхождение раньше решалось бы неявно, на усмотрение момента.

**Почему исходная реализация была недостаточна именно здесь:** источник единичный (только Chief Design Officer) — конкретный порядок приоритета (Decisions → Memory → дневник → knowledge) не клонирован дословно, а выведен из уже существующей архитектуры уровней памяти Foundation, поскольку CDO ранжировал источники по другой оси (доверие к дизайн-суждению, не к слоям памяти).

## OPEN_QUESTIONS.md (новый файл, объём пересмотрен после появления Decision Management / Entry Gate / Sources of Truth / Capability Resolver)

**Источник (Blueprint):** OBSIDIAN_BUILDER, `KNOWLEDGE/OPEN_QUESTIONS.md` (три поля: вопрос / критерий ответа до поиска / статус). Формат статуса — не клонирован повторно, унаследован от уже собранного `DECISIONS.md` (не удаляется, переклассифицируется, явное переоткрытие). Слабое вторичное эхо — AI_OS, эпистемическая лестница ЗНАЕМ/ПРЕДПОЛАГАЕМ/НЕ ЗНАЕМ.

### Проверка ответственности перед проектированием (по прямому требованию владельца)

Перед Blueprint пройдена повторная проверка — не закрылась ли ответственность механизма новыми узлами, появившимися сегодня же (Entry Gate, `DECISIONS.md`, Sources of Truth, Capability Resolver):

- **Entry Gate** — момент «спросить/не спросить» здесь и сейчас, не хранит ничего между сессиями. Не закрывает.
- **`DECISIONS.md`** — близко по форме (append-only, статус, не удаляется), но другое по сути: решение — выбор, утверждаемый явным словом владельца; открытый вопрос — пробел в знании, закрываемый доказательством, не одобрением. Не закрывает ответственность, но формат статуса унаследован оттуда.
- **Sources of Truth** — разрешает конфликт между уже существующими фактами; открытый вопрос — то, чего ни в одном источнике ещё нет. Не закрывает.
- **Capability Resolver** — реальное пересечение: поле «где искать» из исходного описания OBSIDIAN_BUILDER полностью покрывается классификацией потребности в `ROUTING.md`. Поле исключено из нового файла как дублирующее.

**Итог проверки:** самостоятельная ответственность подтверждена (Вариант 1 из трёх рассмотренных), но объём уже, чем в исходном источнике — 3 поля вместо 4.

### Клонировано без изменений

- Правило «критерий ответа фиксируется до начала поиска, не после».
- Принцип «не удаляется, только переклассифицируется» + явное переоткрытие с датой и причиной.

### Не перенесено

- Поле «где искать» — дублирует уже существующий Capability Resolver в `ROUTING.md`.

**Почему новый файл, а не усиление существующего:** ни `MEMORY.md`/`knowledge/` (хранят уже узнанное), ни `DECISIONS.md` (решения среди альтернатив, не пробелы в знании), ни `ROUTING.md` (маршрут к возможности, не хранение вопроса во времени) не владеют ответственностью «нерешённый вопрос как персистентный во времени объект».

**Почему это усиливает Foundation:** защищает от «ну вроде нашли» — закрытия вопроса слабым, подогнанным по факту ответом, потому что критерий зафиксирован заранее, а не постфактум.

**Почему исходная реализация была недостаточна именно здесь:** единичный источник в археологии, но конкретный формат статуса и правило переоткрытия к моменту проектирования уже проверены и работают в `DECISIONS.md` — перенесены как готовый, а не гипотетический паттерн.

## Execution Drift (расширение раздела «Правила» в HOME.md)

**Источник (Blueprint):** MAIN_ENGINEER (Execution Drift — языковые сигналы съезда с роли) — Blueprint_Agent_System (Drift Prevention + Alignment Check) — Chief Design Officer (`Pattern — CDO Drift Modes`, три конкретных срыва + `Review — Project Self-Audit`, требование следа даже при чистом прохождении).

### Проверка ответственности перед проектированием (по прямому требованию владельца — остаться обнаружением, не управлением)

- Разобрана граница: обнаружение и откат к уже установленному поведению — не новое решение (аналогично тому, как Decision Freeze не создаёт решение, а защищает уже принятое). Если возврат к известному не закрывает дело — механизм не чинит это сам, а обязан остановиться и передать через Entry Gate. Написано явно в тексте.
- Проверка по времени в разговоре: Entry Gate — момент входа в задачу; Execution Drift — по ходу уже идущей работы. Разные точки, не пересекаются, оба узла не поглощают друг друга.
- `DECISIONS.md` / Sources of Truth / Capability Resolver / `OPEN_QUESTIONS.md` — ни один не отвечает за поведение агента в моменте разговора. Ответственность подтверждена как самостоятельная, но не как отдельная сущность — как расширение уже существующей ответственности `HOME.md` («Правила» — поведенческие ограничения по ходу работы).

### Усилено (не новая сущность)

- Новый пункт в разделе «Правила» `HOME.md`: заметить дрейф без нарушения явного правила → назвать → вернуться к известному, либо остановиться и передать через «Вход в задачу». Требование следа при чистом прохождении — та же дисциплина, что уже применена в Entry Gate.

### Не перенесено

- Конкретный список языковых сигналов MAIN_ENGINEER («вот что напишем» вместо «вот как устроено») — специфичен для пары ролей архитектор/исполнитель, то есть для инженерной специализации. Foundation не знает загруженной специализации — перенос конкретных сигналов нарушил бы «Foundation сознательно не содержит профессию». Оставлено точкой расширения `SOUL.md`.

**Почему усиление, а не новый файл:** `HOME.md` уже владеет ответственностью «поведенческие ограничения по ходу работы» (анти-галлюцинация, тон-по-SOUL) — дрейф-детекция та же по роду ответственность, не новая.

**Почему это усиливает Foundation:** до этого момента Foundation не различал «нарушил явное правило» и «постепенно съехал, не нарушив ничего напрямую» — второй тип сбоя был полностью невидим.

**Почему исходная реализация была недостаточна именно здесь:** ни один источник по отдельности не даёт одновременно (а) сам механизм обнаружения, (б) границу «откат, не решение», и (в) явное разделение общего механизма (Foundation) и конкретных сигналов (специализация) — собрано из трёх источников в одно расширение одного раздела.

## System Health Check (расширение UPDATE.md)

**Источник (Blueprint):** MAIN_ENGINEER (System Health Check / Anti-Framework Disease, раздел 9) — взята только периодическая часть.

### Проверка ответственности перед проектированием

- **Legacy-first Alarm** (уже в Entry Gate) — ищет дубли перед созданием ОДНОЙ конкретной вещи, привязан к текущей задаче. Health Check не привязан ни к какой задаче, оглядывается на всё сразу. Разные триггеры, не пересекаются.
- **«Три вопроса перед созданием новой сущности»** — вторая половина исходной находки MAIN_ENGINEER — при проверке оказалась уже покрыта: «решает ли это то, что нельзя решить существующим» = Legacy-first Alarm; «согласен ли владелец с ростом сложности» = уже гарантирует Decision Gateway (ничего не становится постоянным без Locked). Не перенесена — была бы чистым дубликатом.
- **Execution Drift** — про поведение агента в разговоре, Health Check — про структуру файлов. Разные объекты обнаружения, не пересекаются.

**Итог проверки:** ответственность подтверждена, но уже источника — только периодический ретроспективный взгляд на накопленную структуру, без «трёх вопросов» (уже покрыты) и без права самостоятельно удалять (та же граница detection-not-management, что у Execution Drift).

### Усилено (не новая сущность)

- Новый раздел «Периодическая проверка накопленной сложности» в `UPDATE.md`: триггер — прямая просьба владельца или подключение крупной новой специализации (не расписание, не каждая сессия); проверяет дубли `skills/`/`knowledge/`, файлы без читателей, устаревшие Locked-записи в `DECISIONS.md`; результат — отчёт владельцу, решение об удалении — через `DECISIONS.md`, не самостоятельно.

**Почему усиление, а не новый файл:** `UPDATE.md` уже владеет ответственностью «состояние служебного слоя дома» (защита при обновлении, Self-Modification Guard) — Health Check расширяет её с «не сломать при обновлении» до «не обрасти мусором со временем», та же родовая ответственность.

**Почему это усиливает Foundation:** технический checksum-контроль в `UPDATE.md` защищал от потери файлов при обновлении, но ничего не проверял в смысловой сложности — дублей, мёртвых файлов, устаревших решений. Раньше это было полностью не видно.

**Почему исходная реализация была недостаточна именно здесь:** MAIN_ENGINEER даёт периодическую проверку в связке с «тремя вопросами», которые на момент проектирования оказались избыточны — Foundation v2 к этому моменту уже закрыл ту часть другими узлами (Legacy-first Alarm, Decision Gateway), поэтому перенесена только половина находки.
